## 2. 项目一：VirtualBench —— 虚拟测试设备与 Qt 上位机

### 2.1 项目定位

使用 **C++17 + CMake + Qt Widgets**，自主构建一个虚拟采集设备与上位机联调系统，覆盖：

- 独立设备模拟器：响应指令、生成多通道模拟波形数据。
- 自定义二进制 TCP 协议：编码、解码、CRC、半包合包、错误数据恢复。
- 上位机：连接/启动/停止、设备状态、曲线、日志、配置。
- 稳定性：通信超时、断线重连、缓存上限、异常输入测试。
- 工程能力：SQLite 历史数据、CMake、测试、性能报告、Windows/Linux 编译验证（环境允许时）。
- **默认差异化模块：** ONNX Runtime 异常检测（主打端侧 AI 设备软件）；时间紧张时优先做可解释的最小闭环。
- **明确保留的可选扩展：** Modbus TCP（以后有时间再做，面向工业上位机/ATE/仪器岗位），**不影响上述必做任务和 ONNX 计划**。

> 注意：本项目是**个人模拟设备系统**，不是生产级 PLC、真实 ATE 或工控现场经验；简历中据实说明。

### 2.2 架构：从简单方案逐步演进

**第一版（必须先做）**

```text
 device_simulator (C++17，TCP 服务端)
       │  自定义协议：HELLO / START / STOP / DATA / STATUS
       │  TCP 长连接
       ▼
 host_gui (Qt Widgets，客户端)
       │
       ├─ QTcpSocket 异步收发 + 连接状态管理
       ├─ StreamParser 增量解析字节流
       ├─ DeviceService 命令/状态/数据分发
       ├─ QTimer 合批刷新曲线与状态
       └─ SQLite 数据存储（第二阶段加入）

 共享静态库 protocol（不依赖 Qt GUI / Socket）
 ├─ Frame
 ├─ ProtocolCodec（完整帧编解码 + CRC）
 └─ StreamParser（任意数据块输入 → 0~N 个完整帧）
```

**只有压测或可靠性需求证明必要时，才升级为：** I/O 工作对象、后台解析/入库线程、有界队列、SPSC 环形缓冲等。`QTcpSocket` 是异步事件驱动 API，**不因“网络通信”四个字就强行创建线程**。

### 2.4 协议 V1：开发前冻结约定

**二进制帧（网络传输数据采用本项目自定义小端格式）**

| 字段 | 字节数 | 说明 |
|---|---:|---|
| `magic` | 2 | 固定 `A5 5A`（字节序列） |
| `version` | 1 | `0x01` |
| `cmd` | 1 | 命令号 |
| `payload_len` | 2 | 无符号小端整数，最大 **4096 B** |
| `payload` | N | N 字节，按命令分别约定字段 |
| `crc16` | 2 | CRC16-Modbus 算法，小端存储；仅覆盖 `version` 到 `payload` 最后一字节 |

一帧固定开销 **8 B**、上限 **4104 B**。CRC16-Modbus 是**校验算法名称**，并不代表此协议就是 Modbus TCP/RTU。

| 命令 | 数值 | 方向 | 负载 |
|---|---|---|---|
| `HELLO` | `0x01` | host→device | 协商协议版本（具体结构写入 `docs/protocol.md`） |
| `START` | `0x02` | host→device | 采样率 `u32` + 通道掩码 `u8` |
| `STOP` | `0x03` | host→device | 空 |
| `DATA` | `0x04` | device→host | `chan_id:u8`、`seq:u32`、`ts:u64`、`cnt:u16`、`float32[cnt]` |
| `STATUS` | `0x05` | device→host | 状态码 |
| `ACK` | `0x06` | device→host | 被确认命令 `u8` + 结果 `u8` |
| `ERROR` | `0x7F` | device→host | 错误码和有长度限制的描述 |

补充规则：

1. 所有多字节整数与 `float32` 均按约定显式序列化为**小端**；浮点格式使用 IEEE 754 binary32。**禁止直接把 C++ 结构体内存 `reinterpret_cast` 后发送**。
2. `DATA` 的 payload 长度必须等于 `15 + 4 × cnt`；最大 `cnt` 受 `payload_len` 限制；`seq` 是每通道递增的 `uint32_t`，允许正常回绕。
3. `ts` 是**模拟器启动后的单调时间，单位微秒**；跨进程时延统计使用可比较的主机时钟/明确的测量边界，不能随意相减两个不同时钟。
4. V1 **同一连接同时最多一个待确认控制命令**，可用 ACK + 超时实现；未来确实需要并发命令时，再设计 request_id。
5. `ProtocolCodec` 处理**完整帧**；`StreamParser` 处理 TCP **流式增量输入**；业务层判断未知命令并响应错误。
6. `StreamParser` 必须限制 payload/缓存大小：收到不完整帧先保留；CRC 错误时不能直接丢弃其后的合法帧，应寻找下一个 magic 重新同步；对于伪造的合法长度但缺少后续字节，还需通过接收超时/连接复位策略避免无限等待。
7. 以上是 **V1 建议规格**。W1 与 Codex 一起审查后更新 `docs/protocol.md`，后续编码以协议文档为唯一标准，不允许设备端和上位机各自修改解释。

### 2.5 W1 必须掌握的三项核心接口

```cpp
// 仅用于明确职责和 API 方向，不是可直接编译的完整实现。
struct Frame {
    std::uint8_t version;
    Command command;
    std::vector<std::uint8_t> payload;
};

// 完整帧序列化 / 反序列化 / CRC 计算。
class ProtocolCodec;

// feed 任意字节块；缓存半帧；每次可能返回 0 / 1 / 多帧。
class StreamParser;
```

**学习与验收重点：** `std::vector<uint8_t>` 的生命周期、边界检查、大小端、`size_t` 与整数溢出、CRC、内存布局、TCP 字节流没有消息边界。

**协议级：**

- [ ] 完整帧编码/解码一致，包含空 payload 和最大合法 payload。
- [ ] 固定已知数据 CRC 测试通过（避免“编码和解码都写错却互相通过”）。
- [ ] 1 帧按任意位置切成 2 段、多个段、每次 1 字节输入，结果一致。
- [ ] 2～N 帧合并输入，可逐帧提取。
- [ ] magic 前有脏字节、CRC 错、非法版本、超长负载时处理符合协议文档。
- [ ] 错误帧后存在合法帧时能重同步；内部缓存有可解释的上限。
- [ ] 随机切分同一批合法数据多次运行，结果一致；编译器 Sanitizer（环境支持时）未报越界。

**联调级：**

- [ ] HELLO/START/STOP 有明确响应和超时反馈。
- [ ] 模拟器退出、网线断开等模拟故障后 UI 不冻结，重连逻辑可恢复或清楚报错。
- [ ] UI 采样显示频率和采样数据频率分离；超过显示能力时按设计降采样/限量。
- [ ] SQLite 批量写入有实际测试，数据可靠性策略明确。

### 2.9 ONNX 默认任务（V3.0 主线保持不变）

1. 模拟器输出正常/异常波形（漂移、阶跃、噪声叠加）；清晰定义训练/测试数据来源。
2. Python 侧训练轻量模型（小型 1D-CNN 或自编码器即可），导出 ONNX，保留模型输入形状和预处理参数。
3. C++ 使用 ONNX Runtime 加载模型，复用 Session；推理不要阻塞 Qt UI 或网络事件循环。
4. 使用**同一批输入、同一预处理**比较 Python 与 C++ 输出，记录误差，不强行承诺达到 `1e-5`。
5. 记录纯模型耗时与从主机收到数据到告警显示的耗时；说明测试机器和计时边界。
6. 如 W7 时间不足，优先保证**简单模型 + C++ Runtime 跑通 + 可验证对齐**；不追求 Transformer、INT8、GPU 多后端。核心通信不稳时，ONNX 可以顺延。

### 2.10 Modbus 未来扩展备忘（**选做，不进入当前 8 周必做计划**）

## 3. 项目二：mini-log —— 轻量异步日志库

### 3.1 项目定位

证明现代 C++、线程安全、资源管理和性能测试能力，补强“只做 Qt GUI”的简历印象。独立 C++17/CMake 小库，**不依赖 Qt**。

### 3.2 先正确再优化的架构

```text
多个业务线程（多个生产者）
          │
          ▼
带锁、有限容量的共享队列（MPSC 语义）
          │
          ▼
一个后台日志线程（消费者）→ 批量写文件 → 滚动文件
```

**关键纠错：** 多个业务线程同时写**同一队列**是**多生产者**场景，不能无保护地套用 SPSC（单生产者单消费者）环形缓冲。先写带锁版；只有测试证明确有价值才研究双缓冲、逐线程 SPSC、原子内存序和伪共享。

### 3.3 六周计划

| 周次 | 时间 | 交付物 | 要掌握的知识 |
|---|---|---|---|
| M1 | 12/07–12/13 | 同步日志：级别、时间、格式、文件写入、基本测试 | RAII、文件生命周期、异常安全 |
| M2 | 12/14–12/20 | 多生产者 + 单消费者的带锁有界队列、工作线程 | mutex、condition_variable、线程结束顺序 |
| M3 | 12/21–12/27 | 队列满策略、退出 flush、按大小滚动文件 | 背压、丢日志计数、数据一致性 |
| M4 | 12/28–01/03 | 压测基线与正确性测试 | 吞吐量、P50/P99 延迟、测试条件 |
| M5 | 01/04–01/10 | 根据瓶颈选一种优化并对比 spdlog | 内存分配、批处理、锁竞争；可选双缓冲 |
| M6 | 01/11–01/17 | 冻结功能、README、压测报告、面试项目介绍 | 用实测解释设计决策与边界 |

**诚实限制：** 异步日志异常崩溃可能丢失队列内未落盘数据；不能承诺任意信号处理器里安全 `flush`。无锁 SPSC、`alignas(64)` 和 lock-free 不列为必须交付物。
