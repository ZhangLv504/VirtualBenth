## W1/S2｜协议边界与控制语义

### 1. 为什么线上帧包含 `payload_len`，内存中的 `Frame` 却不建议保存它？

**参考答案：**

线上字节流没有 C++ 容器的边界信息，接收端必须依靠 `payload_len` 判断需要读取多少字节。内存中的 `Frame` 已使用 `std::vector<std::uint8_t>` 保存 payload，其长度可以由 `payload.size()`唯一推导。若同时保存 `payload_len`，修改 payload 后可能忘记同步长度，形成两个互相矛盾的数据源。因此编码时由 `payload.size()`计算长度，解码时先校验线上长度，再构造 `Frame`。

### 2. 为什么 payload 上限为 4096B 时，DATA 的最大 `cnt` 是 1020，而不是 1024？

**参考答案：**

DATA payload 除样本外还有 15B 固定字段：`chanId` 1B、`seq` 4B、`ts` 8B、`cnt` 2B。每个 `float32` 样本占 4B，因此：

```text
15 + 4 × cnt ≤ 4096
cnt ≤ floor((4096 - 15) / 4) = 1020
```

`cnt=1020` 时 payload 为 4095B；`cnt=1021` 时为 4099B，已经超限。

### 3. ACK 和 STATUS 分别解决什么问题？

**参考答案：**

TCP 负责字节可靠传输，但不表示对端业务已经成功处理命令。ACK 表示对端应用层已经识别并成功处理指定控制命令；STATUS 表示设备当前状态，既可以跟在控制命令后发送，也可以因设备状态自行变化而主动发送。STATUS 不能替代 ACK。

**纠偏要点：** ACK 不只是证明“对端收到字节”，而是确认应用层命令处理成功。

### 4. 为什么“同一连接最多一个待确认控制命令”可以暂时不设计 `request_id`？

**参考答案：**

任一时刻只有一条 HELLO、START 或 STOP 等待结果，因此收到的匹配 ACK 或 ERROR 可以唯一归属于当前命令，不需要额外关联编号。如果允许多条命令并发在途，仅凭命令类型无法可靠匹配请求与响应，此时才需要 `request_id`。

### 5. 为什么读到 `payload_len=4097` 后不能继续等待 payload？

**参考答案：**

4097 虽然能由 `uint16` 表示，但违反协议规定的 4096B 上限，可能来自数据损坏、错误实现或恶意输入。继续等待会让攻击者利用伪造长度占用缓存并拖延解析，因此解析器应立即把当前候选帧判为非法，滑动一个字节后重新寻找 magic。

**纠偏要点：** 4097 不一定是“长度计算错误”，更准确地说是“违反协议边界”。

### 6. 非法长度或 CRC 错误后，为什么只滑动一个字节，而不是按声明长度丢弃整帧？

**参考答案：**

当前 magic 可能是假起点，声明长度也不可信；它后面的任意字节都可能是真正合法帧的 magic 开头。一次丢弃整段可能跳过后续合法帧。滑动一个字节再搜索能保留所有可能的同步起点。固定帧最小长度为 8B，不存在“整帧长度为 0”；只有 payload 长度可以为 0。

## W1/S2｜时间戳设计

### 7. 为什么后一帧的绝对时间戳变小，不能直接判定网络乱序？

**参考答案：**

UTC Unix Epoch 时间来自系统墙上时钟，可能因 NTP 校时、人工修改或虚拟机时钟调整而跳变或回拨。帧顺序和丢帧应以每通道递增的 `seq` 判断；`ts` 用于跨系统时间关联和历史查询。时间戳回拨应记录为时钟异常，而不是直接认定网络乱序。

### 8. 为什么时间戳单位是微秒，不等于设备具有微秒级时间精度？

**参考答案：**

微秒只是字段的表示分辨率。实际精度还受操作系统时钟源、调度延迟、采样时刻定义、NTP/PTP 同步质量及硬件能力影响。协议可以保存到 1μs，但不能据此宣称测量结果具备 1μs 准确度。

### 9. ACK 超时为什么应使用单调时钟，而不能使用 UTC Unix Epoch 时间？

**参考答案：**

超时测量关心经过了多长时间，需要时间只向前推进。UTC 系统时间可能跳变或回拨，可能导致超时提前、延后甚至长时间不触发。`std::chrono::steady_clock` 等单调时钟适合测量持续时间；UTC Unix Epoch 时间适合记录事件发生的绝对时间。

## W1/S3｜Frame 数据模型

### 10. 为什么 `Command::Invalid` 不能被编码发送？

**参考答案：**

`Invalid=0x00` 是内存中的安全默认状态，用来暴露“尚未选择命令”的对象。它不是协议命令表中的合法线上值。编码器遇到 `Invalid` 应返回错误，防止默认构造的半成品对象被误发给对端。

### 11. 为什么当前的 `Frame` 不需要 `.cpp` 文件？

**参考答案：**

当前 `Frame` 只有枚举、常量和数据成员，没有需要放到翻译单元中的非内联函数实现。声明全部放在头文件即可。保留并编译空的 `frame.cpp` 只会增加无意义的构建输入；以后若加入适合放在源文件中的实现，再创建对应 `.cpp`。

## W1/S3｜Catch2 基础测试

### 12. `TEST_CASE` 和 `REQUIRE` 分别做什么？

**参考答案：**

`TEST_CASE` 定义一个可以独立运行和报告结果的测试场景，名称应描述被验证的行为。`REQUIRE(expression)` 断言表达式必须为真；如果为假，当前测试立即失败，并报告失败位置和表达式。一个测试用例可以包含多个相关断言。

### 13. 为什么检查 `enum class Command` 的数值时需要 `static_cast<std::uint8_t>`？

**参考答案：**

`enum class` 是强类型枚举，不会隐式转换为整数。这能减少把不同枚举或整数意外混用的问题。测试线上协议值时，需要显式转换为其底层类型，再与 `0x01`、`0x06` 等字节值比较。

### 14. 为什么要测试命令枚举的具体数值，而不只测试枚举成员是否存在？

**参考答案：**

命令数值属于设备端和上位机共同遵守的线上协议。枚举成员即使能够编译，只要某个数值被误改，双端就可能把同一个字节理解为不同命令。测试具体数值可以锁定协议映射，在后续修改时及时发现破坏兼容性的变更。

### 15. 为什么 CTest 显示 1 个测试，而 Catch2 报告 5 个测试用例？

**参考答案：**

CMake 的 `add_test` 把整个 `protocol_tests` 可执行程序注册为一个 CTest 测试，所以 CTest 显示 `1/1`。这个可执行程序内部包含多个 Catch2 `TEST_CASE`，由 Catch2 继续发现、执行并统计，因此本次报告为 5 个测试用例、21 个断言。两者统计的是不同层级。

### 16. 为什么验收时要确认构建日志中确实重新编译了 `test_frame.cpp`？

**参考答案：**

增量构建可能直接运行之前生成的旧测试程序。如果只看到测试通过，却没有确认新测试源文件已参与编译和链接，就可能把旧二进制的结果误认为当前代码的结果。本次构建日志明确出现 `test_frame.cpp` 并重新生成 `protocol_tests.exe`，因此后续测试结果可以证明当前 Frame 测试已实际执行。

## W1/S4｜ProtocolCodec 编码

### 17. 为什么编码 `payload_len` 和 CRC 时不能直接复制本机整数的内存？

**参考答案：**

本机整数的内存字节序取决于 CPU 平台，直接复制还可能受到类型大小、对齐和对象表示的影响；协议要求线上格式始终为显式小端。编码时应通过移位和掩码分别写入低字节、高字节，使结果与运行平台无关，也避免把 C++ 对象内存布局当成网络协议布局。

### 18. 为什么 CRC 从 `version` 开始计算，而不覆盖 magic 和帧尾 CRC？

**参考答案：**

这是冻结协议明确规定的覆盖范围：`version + command + payload_len + payload`。magic 用于在字节流中寻找同步起点；若 magic 损坏，解析器会把它当作噪声并继续寻找下一处 magic。帧尾 CRC 是待比较的校验结果，不能把自身加入计算，否则编码端和接收端无法按同一规则验证。

### 19. 为什么 `ProtocolCodec::encode()` 只校验帧级约束，而不在这一层检查 START 采样率或 DATA 的 `cnt`？

**参考答案：**

`ProtocolCodec` 的职责是把通用 Frame 安全地转换为线上字节，包括版本、合法命令、最大 payload、大小端和 CRC。START 参数、DATA 样本结构等属于具体命令的业务语义，应由构造命令 payload 的业务层或专门的 payload 编解码函数校验。分层可以避免通用帧编解码器不断膨胀，也让帧级测试与业务级测试彼此独立。

### 20. 把 payload 复制到输出缓冲区后，为什么必须同步推进写入位置 `pos`？

**参考答案：**

`pos` 表示下一个待写字节的位置。复制 payload 后如果不执行 `pos += payload_len`，后续 CRC 会从 payload 起始位置写入，覆盖 payload 的前两个字节；空 payload 因长度为 0 可能碰巧通过，从而掩盖这个错误。START 等非空 payload 的精确字节测试能够暴露该问题。

### 21. 调用 CRC 函数时，起始指针和长度应该如何确定？

**参考答案：**

协议规定 CRC 覆盖 `version + command + payload_len + payload`。完整缓冲区中 version 位于偏移 2，因此起始指针应指向 `bytes.data() + 2`，长度为 `4 + payload_len`。不能从 `bytes.data()`开始，也不能把 magic 或尚未写入的帧尾 CRC 空间纳入计算。

### 22. 为什么在 C++17 中不能直接写 `ProtocolCodec::encode(frame) == EncodeResult{}`？

**参考答案：**

自定义结构体不会在 C++17 中自动生成 `operator==`，而 `EncodeResult` 也没有手写比较运算符，因此该表达式无法编译。测试应分别检查语义，例如先保存结果，再使用 `REQUIRE(result.ok())` 和 `REQUIRE(result.bytes == expected)`。即使定义结构体整体相等，拿成功结果与默认的空结果比较也不能验证正确编码出的帧内容。

## 项目协作｜新会话交接

### 23. 为什么要把 `AGENTS.md` 与 `PROJECT_PROGRESS.md` 分开？

**参考答案：**

`AGENTS.md` 保存长期稳定、需要每次会话遵守的规则，例如导学方式、测试授权和文档优先级；`PROJECT_PROGRESS.md` 保存会频繁变化的当前阶段、验证证据、已知问题和下一步。分开后，稳定规则不会被进度细节淹没，也能避免旧阶段状态长期留在自动加载的指令中。

### 24. 为什么新会话读取 `PROJECT_PROGRESS.md` 后，仍然必须检查 Git 和实际文件？

**参考答案：**

进度文档只是某个时间点的人工摘要，可能尚未记录用户刚完成的编辑、暂存区变化或最新测试结果。Git 状态、diff、实际文件和真实测试输出才是当前事实。新会话先读摘要用于快速定位，再用这些证据核对，可以避免重复工作、覆盖未提交修改，或把“已经写入”误报为“已经验证”。

## W1/S4｜ProtocolCodec 编码审查

### 25. 为什么 payload 为空、复制长度为 0 时，仍不应无条件调用 `std::memcpy`？

**参考答案：**

空 `std::vector` 的 `data()` 允许返回空指针，而 `std::memcpy` 要求传入有效指针；不能把“复制 0 字节”当成空指针一定合法。HELLO 和 STOP 都有合法空 payload，因此编码器应仅在 `payload_len > 0` 时调用 `std::memcpy`，随后再统一推进写入位置。

### 26. 为什么 UnsupportedVersion 测试还应把 command 设置为一个合法命令？

**参考答案：**

一个测试最好只引入一个导致失败的条件。若版本非法且 command 仍为默认 `Invalid`，结果会依赖编码器先检查哪个字段；测试实际上锁定了错误检查顺序，而不是单独证明“不支持的版本会被拒绝”。把 command 设为 `Command::Hello` 后，失败原因才唯一来自 version。

### 27. 为什么只判断 `frame.command == Command::Invalid` 仍不能阻止未知命令被编码？

**参考答案：**

`enum class` 能防止普通整数被隐式赋值，但调用方仍可通过 `static_cast<Command>(0x55)` 构造一个枚举声明中不存在的值。只排除 `Invalid(0x00)` 会让该未知值被原样写入线上帧。编码器应明确接受当前协议定义的命令集合，其余未定义或预留值统一返回 `InvalidCommand`。

### 28. `std::vector<std::uint8_t>` 的 `operator==` 会比较什么？

**参考答案：**

它比较两个 vector 的元素数量以及每个对应位置的元素，只有长度相同且全部元素按顺序相等时结果才为真。因此 `result.bytes == expected` 可以验证完整帧的总长度、字节顺序和每个字节的值。

### 29. 在精确示例测试中，为什么 `result.bytes == expected` 后通常不必再单独断言长度？

**参考答案：**

vector 相等本身已经要求长度相同。如果实际结果多一个或少一个字节，相等比较就会失败。单独检查长度只有在希望把“长度错误”和“内容错误”分别报告，或者测试本身只关心长度边界时才有额外价值。

### 30. 为什么 `payload_len` 可以使用 `std::uint16_t`，而 `total_len` 和 `pos` 更适合使用 `std::size_t`？

**参考答案：**

`payload_len` 对应协议中固定的 2 字节无符号字段，使用 `std::uint16_t` 能表达其线上宽度。`total_len` 和 `pos` 用于表示 C++ 容器的大小与下标，应与 `vector::size()` 的类型一致，使用 `std::size_t` 可以避免有符号/无符号混用和不必要的窄化转换。

### 31. 为什么错误路径除了检查错误码，还应检查 `result.bytes.empty()`？

**参考答案：**

错误码证明编码器识别了非法输入，而空输出证明它没有同时泄漏一段不完整或不可发送的帧。两项一起断言，才能锁定“失败时不产生线上数据”的接口契约。

### 32. 为什么 4096B 边界测试还要检查编码后的长度字段和 payload 首尾字节？

**参考答案：**

只检查输出总长 4104B，无法证明 `payload_len` 被正确写成小端 `00 10`，也无法证明整个 payload 被放在正确位置。增加长度字段及 payload 首尾检查，可以更有针对性地发现端序错误、偏移错误或边界处漏写数据。

### 33. 为什么本次既要确认构建成功，又要确认测试成功？

**参考答案：**

构建成功只证明当前源码能够完成编译和链接，例如标准库头、类型名称和函数声明没有阻止生成程序；测试成功才进一步证明程序在已覆盖场景中的行为符合预期。测试程序无法生成时谈不上执行，能生成也不代表编码逻辑一定正确，因此两种证据缺一不可。

### 34. 为什么构建日志中重新出现 `protocol_codec.cpp` 和 `test_protocol_codec.cpp` 很重要？

**参考答案：**

这证明刚修改的实现和测试实际参与了本次编译，运行的不是修改前遗留的旧测试程序。只有重新编译、重新链接后得到的可执行程序，其测试结果才能作为当前工作区的验证证据。

### 35. 12 个测试用例、43 个断言全部通过，为什么还不能说明 `decode()` 已经完成？

**参考答案：**

测试结论只覆盖本次实际编译和执行到的功能。当前新增用例验证的是 encode，已有用例验证 Frame 和 CRC；`decode()` 尚未实现，也没有对应测试。通过数量不能替代覆盖范围分析，因此只能宣布 encode 里程碑通过，不能把后续功能一并视为完成。

### 36. 为什么 VS2022 Debug 测试通过，仍不能替代项目默认的 VS2019 RelWithDebInfo 验收？

**参考答案：**

不同编译器版本和构建配置可能暴露不同的问题，例如标准库实现差异、警告与优化行为、宏定义以及只在优化后出现的未定义行为。VS2022 Debug 通过是有价值的补充证据，但项目声明的默认交付环境是 VS2019 RelWithDebInfo，因此最终阶段结论必须包含默认环境的实际构建和测试结果。

### 37. 为什么项目可以同时使用“VS2019 工具链”和“Ninja 生成器”？

**参考答案：**

编译器工具链负责把 C++ 源码编译、链接成程序，本项目当前使用 VS2019 提供的 `cl.exe`；CMake 生成器负责生成并驱动构建规则，当前使用 Ninja。Ninja 可以调用 VS2019 的编译器，因此两者描述的是构建链的不同层次，并不冲突。

### 38. 新会话能够读取根目录 `AGENTS.md`，为什么仍建议发送新会话启动指令？

**参考答案：**

`AGENTS.md` 适合保存长期稳定的仓库规则；启动指令会明确要求新会话读取动态的 `PROJECT_PROGRESS.md`、核对 Git 和实际工具链，并指出当前唯一任务。两者配合既避免把易过期的进度塞进长期规则，也能让新会话快速恢复到正确阶段。

## 项目协作｜默认环境复验前核对

### 39. 为什么不能仅凭目录名 `cmake-build-relwithdebinfo` 判断默认构建环境？

**参考答案：**

目录名只是人为约定，可以被误命名、复制或保留旧配置；真正决定构建行为的是目录内的 CMake 缓存和编译器识别结果。运行前应核对 `CMAKE_BUILD_TYPE`、`CMAKE_GENERATOR`、`CMAKE_CXX_COMPILER` 以及编译器 ID/版本，才能确认当前目录实际使用的是 RelWithDebInfo、Ninja 和预期的 MSVC 工具链。

### 40. `git status` 中新文件显示 `AM` 时，为什么必须同时查看 `git diff` 和 `git diff --cached`？

**参考答案：**

`AM` 表示该新文件已经有一个版本进入暂存区，同时工作区又在暂存版本之上继续修改。`git diff --cached` 显示暂存区相对 HEAD 的内容，`git diff` 显示工作区相对暂存区的内容；只看其中一个会漏掉另一层变化，可能误判实际实现或在后续操作中覆盖用户工作。

### 41. CMake 缓存确认了 VS2019、Ninja 和 RelWithDebInfo，为什么仍不能说当前 encode 已在默认环境通过？

**参考答案：**

CMake 缓存只能证明该构建目录配置为这些工具和构建类型，不能证明最新源码已经被重新编译，更不能证明测试已经执行成功。只有在当前工作区上实际构建目标，并运行 CTest 与测试可执行程序、记录真实输出后，才能把 encode 标记为已在默认环境验证。

## W1/S4｜默认环境复验结果

### 42. `ninja: no work to do` 表示什么，为什么不能把它写成“本次重新编译了源码”？

**参考答案：**

它表示 Ninja 根据当前依赖图、输入和产物状态判断目标已经是最新的，因此构建命令成功但没有执行新的编译或链接动作。这可以作为目标未过期的证据，却不能伪装成本次日志中重新出现了编译步骤；应如实记录 `no work to do`，并结合已有 Ninja 构建记录、目标命令和随后实际运行的测试判断当前产物。

## W1/S4｜ProtocolCodec 解码设计

### 44. 为什么完整帧 `decode()` 不应该负责在缓存中搜索 magic、保留半包或消费字节？

**参考答案：**

这些操作依赖连续多次网络输入和缓冲区状态，属于流式 `StreamParser` 的职责。完整帧 `decode()` 应只校验并转换调用方交给它的一帧精确字节，使它保持无状态、输入输出清晰且容易单测。未来 StreamParser 负责找 magic、读取声明长度、等待整帧和重同步，然后把切出的单帧交给 decode。

### 45. 只读解码时，为什么参数通常应使用 `const std::vector<std::uint8_t>&`，而不是按值接收 vector？

**参考答案：**

按值接收会复制整个 vector，而解码只需要读取输入，并不需要拥有或修改它。使用常量引用可以避免最多 4104B 的无意义复制，同时通过类型约束表达“函数不会修改调用方字节”。如果以后需要支持任意连续内存，可再考虑指针加长度或 C++20 的 `std::span`，但当前 C++17 下常量引用足够清晰。

### 46. 为什么 `DecodeResult` 默认 `error=None` 容易造成失败开放？

**参考答案：**

只要某条尚未完成或遗漏的分支直接返回默认构造的结果，`ok()` 就会报告成功，即使 `frame` 仍是默认的 `Command::Invalid`。当前骨架在 magic 正确且长度至少 6B 时正会出现这种情况。解码器应采用失败关闭的默认状态，或确保只有完成所有长度、CRC、版本和命令校验并构造 Frame 后，才显式产生 `None` 成功结果。

### 47. 测试非法版本或未知命令时，为什么要重新计算一个正确的 CRC？

**参考答案：**

如果只修改版本或命令字而保留旧 CRC，帧同时具有 CRC 错误和语义错误，解码器可能会先正确返回 `CrcMismatch`，测试便无法单独证明版本或命令校验。重新计算正确 CRC 后，帧只保留目标无效条件，才能稳定验证 `UnsupportedVersion` 或 `InvalidCommand`。

### 48. 为什么最大 payload 的 encode/decode round-trip 不能替代协议文档中的固定示例测试？

**参考答案：**

如果 encode 和 decode 对同一个字段采用了相同的错误规则，两者可能互相抵消，使 round-trip 仍然通过。协议文档中的 HELLO、START 固定字节帧提供独立的外部基准；round-trip 适合验证双向一致性和 4096B 边界，但必须与固定向量测试配合。

### 49. 为什么解码失败测试还要确认返回的 `Frame` 保持默认无效状态？

**参考答案：**

错误码说明输入不可接受，而默认无效 Frame 可以防止调用方误用只解析了一部分、尚未通过 CRC 或语义校验的数据。只有全部校验完成后才暴露有效 Frame，能把“错误结果”和“可信业务数据”明确分开。

### 50. 小端的 `payload_len` 应如何从 `bytes[4]` 和 `bytes[5]` 还原？

**参考答案：**

`bytes[4]` 是低字节，应直接放在低 8 位；`bytes[5]` 是高字节，应先转换为足够宽的无符号类型再左移 8 位，最后按位或组合，即语义上为 `bytes[4] | (bytes[5] << 8)`。若写成 `bytes[4] << 8 | bytes[5]`，就按大端解释了，例如线上 `05 00` 会被误读成 1280 而不是 5。

### 51. 为什么复制解码后的 payload 前必须先调整 vector 大小，而且源偏移应为 6？

**参考答案：**

默认构造的 `frame.payload` 大小为 0，没有可供写入的元素；直接向其 `data()` 复制非零字节会写入无效存储。应先 resize 或按迭代器范围赋值。线上 payload 从完整帧偏移 6 开始，偏移 4 和 5 是 `payload_len`，从偏移 4 复制会把长度字段误当成 payload。payload 为空时应跳过 `memcpy`。

### 52. 解码时 CRC 的读取字节序和计算覆盖范围分别是什么？

**参考答案：**

帧尾 CRC 按小端存储，因此偏移 `6 + payload_len` 是低字节，下一字节是高字节。重新计算时必须从完整帧偏移 2 的 version 开始，覆盖 `version + command + payload_len + payload`，总长度为 `4 + payload_len`；不能只对 payload 计算，也不能把 magic 或帧尾 CRC 纳入范围。

### 53. 为什么读出 `payload_len` 后必须先检查 4096B 上限，再判断完整帧是否收齐？

**参考答案：**

超过 4096B 的声明本身已经违反协议，不应继续信任该长度或等待攻击者承诺的大块 payload。先检查上限可以立即返回 `PayloadTooLarge`，让未来 StreamParser 从当前候选 magic 滑动一个字节重新同步；若先检查完整长度，4097B 头会被误判成普通半包并长期占用缓存。

### 54. 精确单帧 decode 为什么既要检查输入小于预期长度，也要检查输入大于预期长度？

**参考答案：**

输入小于 `8 + payload_len` 表示帧尚不完整，应返回 `IncompleteFrame`；输入大于该长度表示调用方传入了尾随数据或多帧粘连，不符合“只解一帧精确字节”的接口契约，应返回 `FrameSizeMismatch`。只有大小完全相等，后续 CRC 偏移和 payload 边界才具有唯一含义。

### 55. 为什么完整帧结构确定后，通常先校验 CRC，再判断版本和命令是否合法？

**参考答案：**

版本和命令字也位于 CRC 覆盖范围内。如果传输损坏改变了这些字节但 CRC 未同步变化，先做语义判断会把损坏帧误报成版本或命令错误。先通过 CRC 确认受保护字节整体一致，再对具有正确 CRC 的帧返回 `UnsupportedVersion` 或 `InvalidCommand`，错误分类更可靠。

### 56. 核心代码注释为什么应优先解释设计意图和约束，而不是逐行翻译语法？

**参考答案：**

代码本身已经能表达赋值、判断和循环等“做了什么”，逐行翻译容易形成噪声，并可能在代码修改后变得过时。高价值注释应记录代码难以自行表达的原因、协议约束、职责边界和安全不变量，例如为什么超长长度必须立即拒绝、CRC 覆盖哪些字节，以及为什么失败时不能暴露部分 Frame。

### 57. 为什么要在 `decode()` 接口旁明确写出“只接受一帧精确字节”？

**参考答案：**

这句话定义了调用方与解码器的边界：输入不足返回 `IncompleteFrame`，输入有尾随字节返回 `FrameSizeMismatch`；找 magic、等待半包、拆分粘包和消费缓存则由 StreamParser 负责。若接口没有明确该契约，后续调用者可能把多帧缓冲直接交给 decode，或者让 decode 重复承担流式状态管理。

### 58. 为什么要注明解码失败时 `DecodeResult::frame` 必须保持默认无效状态？

**参考答案：**

长度、CRC、版本或命令任一校验失败时，已经读取出的字段都不应被业务层信任。让失败结果保持默认 `Command::Invalid` 和空 payload，可以防止调用方误用部分解析数据；只有全部校验通过后，才把完整 Frame 发布到结果中。

### 59. 为什么要遍历测试 0～5B 的每一种输入长度，而不只测试空输入？

**参考答案：**

固定帧头需要 6B，0～5B 的每个长度都处于“尚不能安全读取完整头部”的边界区间。逐一测试可以证明解码器在任一截断位置都会先返回 `IncompleteFrame`，不会因为已经存在部分 magic、version 或长度字节就越界读取后续字段。

### 60. 为什么 `Command::Invalid(0x00)` 和未知值 `0x55` 都需要独立的解码测试？

**参考答案：**

`Invalid(0x00)` 是枚举中声明的本地默认值，`0x55` 则是枚举声明之外的未知线上值。编码端必须拒绝二者，但 CRC 和长度正确的接收帧需要由 decode 保留原始命令值并交给业务层响应 `UNKNOWN_CMD`。分别测试可以防止 decode 把“已声明但不可发送”和“未声明值”中的任一类错误地当作结构损坏帧丢弃。

### 61. 为什么篡改非空 payload 后保留原 CRC，能够验证 CRC 的覆盖范围？

**参考答案：**

若 CRC 确实覆盖 payload，改变其中任一字节而不更新帧尾 CRC，就会使重新计算值与线上值不一致并返回 `CrcMismatch`。这项测试可以发现“只校验帧头”或“CRC 长度没有包含完整 payload”等覆盖范围错误，同时确认失败结果不会暴露被篡改的数据。

### 62. StreamParser 在缓存中找不到完整 magic 时，为什么仍要保留最后一个 `0xA5`？

**参考答案：**

最后一个 `0xA5` 可能是跨两次接收被拆开的 magic 首字节，下一批数据的第一个字节可能正是 `0x5A`。若把它与前面的噪声一起丢弃，就会漏掉一个合法帧；其他不可能成为 magic 前缀的字节则可以安全丢弃。

### 63. 候选帧出现超长 `payload_len` 或 decode 失败时，为什么只从候选 magic 起丢弃 1B，而不按声明长度或整段候选帧丢弃？

**参考答案：**

当前 magic 可能只是噪声中的伪起点，未经验证的长度也不可信；其后字节中可能已经包含另一个合法 magic。只滑动 1B 后重新搜索，可以避免被恶意或损坏的长度字段带偏，并遵守协议冻结的统一重同步规则。对当前无自重叠的 `A5 5A` 而言，滑动 2B 也不会漏掉 magic，但按声明长度、固定头长或整段候选跳过仍可能越过后方合法帧。

### 64. 为什么 CRC 正确但命令未知的完整帧不能被 StreamParser 当作损坏帧滑动 1B 重同步？

**参考答案：**

它的长度和 CRC 都已经证明帧边界完整可信，未知命令只是业务语义问题。StreamParser 应消费整个完整帧并把原始命令值交给业务层，业务层才能按协议回 `ERROR(UNKNOWN_CMD)`；若滑动 1B，会把一个结构合法的帧误当噪声，还可能在其 payload 内误找 magic。

### 65. 为什么 `feed()` 收到不足 6B 的 chunk 时不能直接返回，而必须先把它追加到内部缓存？

**参考答案：**

TCP 的一次接收可能只包含帧的一小部分，甚至每次只有 1B。当前 chunk 不足 6B 只表示“本次数据不够”，并不表示这些字节无效；必须先追加到跨调用保存的 `buffer_`，再根据整个缓存判断是否能继续，否则分多次到达的 magic、帧头和 payload 都会被丢失。

### 66. 为什么检查 `buffer[0]` 和 `buffer[1]` 不能替代在缓存中搜索完整的 `A5 5A`？

**参考答案：**

合法帧前可能存在任意数量的噪声，而且噪声末尾可能包含多个 `0xA5`。例如 `A5 A5 5A ...` 中第二个 `A5` 才是真正的 magic 起点；若看到第二字节不是 `0x5A` 就一次丢掉前两个字节，会把合法起点一起丢掉。搜索完整二字节序列并按其位置消费前缀，才能正确重同步。

### 67. 为什么 StreamParser 应把精确候选帧交给 `ProtocolCodec::decode()`，而不应再次自行判断版本、命令和 CRC？

**参考答案：**

CRC 和完整帧结构已经由 `ProtocolCodec::decode()` 统一定义，解析器重复实现会产生两套可能不一致的规则。StreamParser 只负责确定候选边界和缓存消费；decode 成功后，即使版本或命令未知，也应把保留原始值的 Frame 交给业务层处理。只有结构或 CRC 解码失败时，解析器才滑动 1B 重同步。

### 68. 候选帧尚未收齐时，为什么解析循环必须返回或跳出，而不能直接 `continue`？

**参考答案：**

候选帧未收齐时缓存没有任何字节被消费，当前调用也没有新数据可以追加。若立即 `continue`，下一轮仍会看到完全相同的缓存和长度条件，形成无限空转。应保留缓存并结束本次解析，等待下一次 `feed()` 带来更多字节。

### 69. 成功解析一帧后，为什么必须消费精确的 `frame_size` 并继续循环？

**参考答案：**

消费少了会把当前帧的尾部误当成下一帧噪声，消费多了会破坏后续粘连帧。只移除已经通过 decode 的精确帧长，才能保持下一字节仍是未处理输入；继续循环则可以在一次 `feed()` 中返回所有已经完整的 0～N 帧。

### 70. 为什么一个最大合法帧为 4104B 的协议，解析循环结束后保留的不完整候选最多只能是 4103B？

**参考答案：**

当合法长度字段最大为 4096B 时，完整帧总长最大是 `8 + 4096 = 4104B`。缓存达到 4104B 就不再是不完整候选：它必须被 decode 成功消费，或因结构/CRC 错误滑动重同步。因此只有少于完整最大帧的 4103B 才可能作为合法但尚未收齐的候选保留。

### 71. 为什么 Git 工作区干净、`main` 与 `origin/main` 一致，仍不能证明当前代码已通过默认环境测试？

**参考答案：**

Git 状态只说明已跟踪内容与当前提交一致、当前分支与远端跟踪分支没有可见差异；它不记录这份提交是否在指定工具链和配置下成功构建或测试。默认环境是否通过，必须由该提交对应的真实构建和测试命令及输出证明。

### 72. 为什么确认默认构建环境时必须读取 `CMakeCache.txt`，不能只根据 `cmake-build-relwithdebinfo` 目录名判断？

**参考答案：**

目录名只是人为命名，不会约束其中实际使用的生成器、编译器或构建类型。`CMakeCache.txt` 才记录该构建树配置时选定的 `CMAKE_GENERATOR`、`CMAKE_CXX_COMPILER` 和 `CMAKE_BUILD_TYPE`；结合编译器识别文件还能确认实际 MSVC 版本，避免把其他工具链的结果误当作默认环境验收。

### 73. 为什么目前不能把 `stream_parser.h` 已提交理解为 `StreamParser` 已实现或至少已被编译器验证？

**参考答案：**

该头文件目前只有接口和伪代码，`protocol/src/stream_parser.cpp` 尚不存在，`protocol/CMakeLists.txt` 也没有把 StreamParser 源文件加入 `protocol` 目标。现有目标不一定包含或实例化这个声明，因此历史构建结果既不能证明三个成员函数已有定义，也不能证明后续实现能够链接和满足流式解析契约。

### 74. 为什么对 `buffer_` 调用 `erase()` 后，不能继续使用此前由 `std::search()` 返回的迭代器？

**参考答案：**

`std::vector` 在删除元素后会使删除位置及其后的迭代器失效，移动元素或重新分配存储时还可能影响更多引用和指针。解析循环每次消费或滑动缓存后都应回到循环顶部重新搜索，不能拿旧迭代器继续计算位置或访问数据。

### 75. 为什么 `payload_len` 的高字节应先转换成足够宽的无符号类型，再左移 8 位？

**参考答案：**

`std::uint8_t` 参与算术时会先发生整数提升；显式转换为 `std::uint16_t` 后再左移，能清楚表达无符号小端组合的意图，避免代码依赖较窄类型、符号扩展或隐式提升规则。最终再与低字节按位或，得到协议规定的 16 位长度。

### 76. 为什么当前实现可以先使用 `vector::erase()` 消费缓存，而不必立即设计环形缓冲或维护复杂游标？

**参考答案：**

当前协议把单帧限制在 4104B，解析器正常结束时的不完整候选最多 4103B，数据规模有限。直接 `erase()` 虽会移动后续字节，但实现简单、边界清晰，足以先验证正确性；只有后续压测证明移动成本成为瓶颈时，才有证据引入读游标、批量压缩或环形缓冲。

### 77. 在缓存中找到 magic 且位置大于 0 后，为什么必须先丢弃 magic 前的噪声，才能读取 `buffer_[4]` 和 `buffer_[5]`？

**参考答案：**

帧字段偏移都是相对于 magic 起点定义的，只有当 magic 已经位于 `buffer_[0]` 时，索引 4 和 5 才是当前候选帧的 `payload_len`。若保留前缀噪声却直接读取固定索引，读到的只是噪声或其他字段；错误长度可能让解析器误判候选帧未收齐，即使后方已有完整合法帧也会停止解析。

### 78. 为什么“清空末尾不是 `0xA5` 的全部噪声”虽然不会漏掉 magic，却仍与当前冻结的 StreamParser 契约不一致？

**参考答案：**

从纯解析正确性看，末尾不是 `0xA5` 时确实不可能与下一批首字节组成 magic；但权威协议和头文件伪代码目前明确规定“找不到 magic 时保留最后 1B”。`buffered_size()` 会让缓存状态成为可观察行为，测试和调用方可能依赖这一契约。若要采用更激进的清空策略，应先统一修改协议、伪代码与测试，而不是只在实现中静默改变。

### 79. 为什么 `payload_len` 和 `frame_size` 最好分别显式声明为 `std::uint16_t` 与 `std::size_t`，而不是都用 `auto`？

**参考答案：**

按位运算的操作数会发生整数提升，因此两个看似为 `std::uint16_t` 的表达式经过 `|` 后，`auto` 可能推导为 `int`。显式类型既记录线上长度字段与容器大小的不同语义，也避免后续在与 `vector::size()`、迭代器偏移比较时发生不明显的有符号/无符号转换。

### 80. 为什么“找到 magic”的判断应是 `magic_idx + 1 < buffer_.size()`，而找不到时才是相反条件？

**参考答案：**

magic 需要当前位置和下一位置两个有效字节，因此只有 `magic_idx + 1` 仍落在容器范围内时，循环才可能在匹配处提前结束。若循环一直走到 `magic_idx + 1 >= size`，说明所有可检查的二字节窗口都不匹配；把条件写反会把成功匹配当成失败，或者在 magic 已位于索引 0 时反复执行空区间删除并无限循环。

### 81. 删除 magic 前缀后，为什么当前实现可以直接继续读取帧头，而不必无条件 `continue`？

**参考答案：**

删除范围精确截止到 magic 起点，删除后 magic 已位于 `buffer_[0]`；代码没有保留或继续使用删除前的迭代器，只使用新的容器大小和固定索引，因此可以立即检查 6B 帧头。重新进入循环也正确，但会重复一次搜索；关键是不能继续使用已经失效的迭代器。

### 82. 为什么把成功解码的 `result.frame` 移入结果数组，比再次复制它更合适？

**参考答案：**

`DecodeResult` 在本轮循环后不再使用，而 `Frame` 内含可能达到 4096B 的 payload。使用 `std::move` 可以把 payload 的动态存储所有权转交给结果数组，通常只需移动容器内部状态，避免再复制一份载荷；移动后不应继续依赖原 `result.frame` 的内容。

### 83. 非法长度候选后面紧跟合法帧时，如果按照非法 `payload_len` 跳过数据，会造成什么后果？

**参考答案：**

非法长度来自尚未通过验证的伪候选头，不能代表真实帧边界。按照它跳过数据可能跨过后方真正的 `A5 5A`，把完整合法帧连同噪声一起删除；解析器随后无法恢复这帧。只滑动 1B 并重新搜索，才能保留所有可能的后续起点。

### 84. StreamParser 在什么条件下才可以一次消费完整的 `frame_size`？

**参考答案：**

只有缓存已经包含 `frame_size` 个字节，并且这段精确候选通过 `ProtocolCodec::decode()` 的结构与 CRC 校验后，当前帧边界才可信。此时才能消费完整帧长；超长长度或 decode 失败时都只能滑动 1B 重新同步。

### 85. 对当前 magic `A5 5A`，为什么滑动 2B 不会漏掉一个从索引 1 开始的新 magic？

**参考答案：**

新 magic 的首字节必须是 `A5`，但当前已确认的索引 1 是 `5A`，所以索引 1 不可能同时成为新 magic 的起点。下一个候选最早只能从索引 2 开始，删除前 2B 仍会保留它。

### 86. 既然滑动 2B 对当前 magic 也安全，为什么实现仍保持滑动 1B？

**参考答案：**

权威协议和冻结伪代码已经明确规定失败时滑动 1B；保持该实现可以让代码、文档和未来测试一致。1B 还是不依赖同步字自重叠性质的统一保守规则，而当前缓存只有几 KB，改成 2B 没有值得改变契约的性能收益。

### 87. 工业实现中，“逻辑上滑动 1B”为什么不等于“必须每次对 vector 执行一次 1B erase”？

**参考答案：**

滑动 1B 描述的是下一次同步搜索必须从当前候选起点之后开始，这是解析语义。实现可以维护读游标，或直接从偏移 1 一次搜索下一个 magic，最后批量删除确认无用的前缀；这样能得到相同解析结果，同时减少反复移动 vector 元素的成本。

### 88. 为什么当前 `vector::erase()` 实现适合 V1，却不一定适合高吞吐工业场景？

**参考答案：**

当前帧最大只有 4104B，直接删除的代码简单、边界清楚，便于先验证正确性。但 `vector::erase()` 会移动后续元素，连续噪声或大量坏帧可能产生重复搬移；高吞吐场景通常改用读游标、批量压缩或环形缓冲，并通过压测判断是否值得增加复杂度。

### 89. 除了重同步规则，一个可长期运行的工业流式解析器还需要哪些保护？

**参考答案：**

至少需要不完整帧超时、缓存和输入资源上限、连续坏帧与 CRC 错误计数、日志和连接处置策略，以及拆包、粘包、噪声、损坏帧和随机分片测试。这些保护分别约束等待时间、内存、CPU 消耗和故障可观测性。
