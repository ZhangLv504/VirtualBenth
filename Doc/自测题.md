## W1/S2｜协议边界与控制语义

### 1. 为什么线上帧包含 `payload_len`，内存中的 `Frame` 却不建议保存它？

**参考答案：**

线上字节流没有 C++ 容器的边界信息，接收端必须依靠 `payload_len` 判断需要读取多少字节。内存中的 `Frame` 已使用 `std::vector<std::uint8_t>` 保存 payload，其长度可以由 `payload.size()`唯一推导。若同时保存 `payload_len`，修改 payload 后可能忘记同步长度，形成两个互相矛盾的数据源。因此编码时由 `payload.size()`计算长度，解码时先校验线上长度，再构造 `Frame`。

### 2. 为什么 payload 上限为 4096B 时，DATA 的最大 `cnt` 是 1020，而不是 1024？

**参考答案：**

DATA payload 除样本外还有 15B 固定字段：`chanId` 1B、`seq` 4B、`ts` 8B、`cnt` 2B。每个 `float32` 样本占 4B，因此：

```text
15 + 4 × cnt ≤ 4096
cnt ≤ floor((4096 - 15) / 4) = 1020
```

`cnt=1020` 时 payload 为 4095B；`cnt=1021` 时为 4099B，已经超限。

### 3. ACK 和 STATUS 分别解决什么问题？

**参考答案：**

TCP 负责字节可靠传输，但不表示对端业务已经成功处理命令。ACK 表示对端应用层已经识别并成功处理指定控制命令；STATUS 表示设备当前状态，既可以跟在控制命令后发送，也可以因设备状态自行变化而主动发送。STATUS 不能替代 ACK。

**纠偏要点：** ACK 不只是证明“对端收到字节”，而是确认应用层命令处理成功。

### 4. 为什么“同一连接最多一个待确认控制命令”可以暂时不设计 `request_id`？

**参考答案：**

任一时刻只有一条 HELLO、START 或 STOP 等待结果，因此收到的匹配 ACK 或 ERROR 可以唯一归属于当前命令，不需要额外关联编号。如果允许多条命令并发在途，仅凭命令类型无法可靠匹配请求与响应，此时才需要 `request_id`。

### 5. 为什么读到 `payload_len=4097` 后不能继续等待 payload？

**参考答案：**

4097 虽然能由 `uint16` 表示，但违反协议规定的 4096B 上限，可能来自数据损坏、错误实现或恶意输入。继续等待会让攻击者利用伪造长度占用缓存并拖延解析，因此解析器应立即把当前候选帧判为非法，滑动一个字节后重新寻找 magic。

**纠偏要点：** 4097 不一定是“长度计算错误”，更准确地说是“违反协议边界”。

### 6. 非法长度或 CRC 错误后，为什么只滑动一个字节，而不是按声明长度丢弃整帧？

**参考答案：**

当前 magic 可能是假起点，声明长度也不可信；它后面的任意字节都可能是真正合法帧的 magic 开头。一次丢弃整段可能跳过后续合法帧。滑动一个字节再搜索能保留所有可能的同步起点。固定帧最小长度为 8B，不存在“整帧长度为 0”；只有 payload 长度可以为 0。

## W1/S2｜时间戳设计

### 7. 为什么后一帧的绝对时间戳变小，不能直接判定网络乱序？

**参考答案：**

UTC Unix Epoch 时间来自系统墙上时钟，可能因 NTP 校时、人工修改或虚拟机时钟调整而跳变或回拨。帧顺序和丢帧应以每通道递增的 `seq` 判断；`ts` 用于跨系统时间关联和历史查询。时间戳回拨应记录为时钟异常，而不是直接认定网络乱序。

### 8. 为什么时间戳单位是微秒，不等于设备具有微秒级时间精度？

**参考答案：**

微秒只是字段的表示分辨率。实际精度还受操作系统时钟源、调度延迟、采样时刻定义、NTP/PTP 同步质量及硬件能力影响。协议可以保存到 1μs，但不能据此宣称测量结果具备 1μs 准确度。

### 9. ACK 超时为什么应使用单调时钟，而不能使用 UTC Unix Epoch 时间？

**参考答案：**

超时测量关心经过了多长时间，需要时间只向前推进。UTC 系统时间可能跳变或回拨，可能导致超时提前、延后甚至长时间不触发。`std::chrono::steady_clock` 等单调时钟适合测量持续时间；UTC Unix Epoch 时间适合记录事件发生的绝对时间。

## W1/S3｜Frame 数据模型

### 10. 为什么 `Command::Invalid` 不能被编码发送？

**参考答案：**

`Invalid=0x00` 是内存中的安全默认状态，用来暴露“尚未选择命令”的对象。它不是协议命令表中的合法线上值。编码器遇到 `Invalid` 应返回错误，防止默认构造的半成品对象被误发给对端。

### 11. 为什么当前的 `Frame` 不需要 `.cpp` 文件？

**参考答案：**

当前 `Frame` 只有枚举、常量和数据成员，没有需要放到翻译单元中的非内联函数实现。声明全部放在头文件即可。保留并编译空的 `frame.cpp` 只会增加无意义的构建输入；以后若加入适合放在源文件中的实现，再创建对应 `.cpp`。

## W1/S3｜Catch2 基础测试

### 12. `TEST_CASE` 和 `REQUIRE` 分别做什么？

**参考答案：**

`TEST_CASE` 定义一个可以独立运行和报告结果的测试场景，名称应描述被验证的行为。`REQUIRE(expression)` 断言表达式必须为真；如果为假，当前测试立即失败，并报告失败位置和表达式。一个测试用例可以包含多个相关断言。

### 13. 为什么检查 `enum class Command` 的数值时需要 `static_cast<std::uint8_t>`？

**参考答案：**

`enum class` 是强类型枚举，不会隐式转换为整数。这能减少把不同枚举或整数意外混用的问题。测试线上协议值时，需要显式转换为其底层类型，再与 `0x01`、`0x06` 等字节值比较。

### 14. 为什么要测试命令枚举的具体数值，而不只测试枚举成员是否存在？

**参考答案：**

命令数值属于设备端和上位机共同遵守的线上协议。枚举成员即使能够编译，只要某个数值被误改，双端就可能把同一个字节理解为不同命令。测试具体数值可以锁定协议映射，在后续修改时及时发现破坏兼容性的变更。

### 15. 为什么 CTest 显示 1 个测试，而 Catch2 报告 5 个测试用例？

**参考答案：**

CMake 的 `add_test` 把整个 `protocol_tests` 可执行程序注册为一个 CTest 测试，所以 CTest 显示 `1/1`。这个可执行程序内部包含多个 Catch2 `TEST_CASE`，由 Catch2 继续发现、执行并统计，因此本次报告为 5 个测试用例、21 个断言。两者统计的是不同层级。

### 16. 为什么验收时要确认构建日志中确实重新编译了 `test_frame.cpp`？

**参考答案：**

增量构建可能直接运行之前生成的旧测试程序。如果只看到测试通过，却没有确认新测试源文件已参与编译和链接，就可能把旧二进制的结果误认为当前代码的结果。本次构建日志明确出现 `test_frame.cpp` 并重新生成 `protocol_tests.exe`，因此后续测试结果可以证明当前 Frame 测试已实际执行。

## W1/S4｜ProtocolCodec 编码

### 17. 为什么编码 `payload_len` 和 CRC 时不能直接复制本机整数的内存？

**参考答案：**

本机整数的内存字节序取决于 CPU 平台，直接复制还可能受到类型大小、对齐和对象表示的影响；协议要求线上格式始终为显式小端。编码时应通过移位和掩码分别写入低字节、高字节，使结果与运行平台无关，也避免把 C++ 对象内存布局当成网络协议布局。

### 18. 为什么 CRC 从 `version` 开始计算，而不覆盖 magic 和帧尾 CRC？

**参考答案：**

这是冻结协议明确规定的覆盖范围：`version + command + payload_len + payload`。magic 用于在字节流中寻找同步起点；若 magic 损坏，解析器会把它当作噪声并继续寻找下一处 magic。帧尾 CRC 是待比较的校验结果，不能把自身加入计算，否则编码端和接收端无法按同一规则验证。

### 19. 为什么 `ProtocolCodec::encode()` 只校验帧级约束，而不在这一层检查 START 采样率或 DATA 的 `cnt`？

**参考答案：**

`ProtocolCodec` 的职责是把通用 Frame 安全地转换为线上字节，包括版本、合法命令、最大 payload、大小端和 CRC。START 参数、DATA 样本结构等属于具体命令的业务语义，应由构造命令 payload 的业务层或专门的 payload 编解码函数校验。分层可以避免通用帧编解码器不断膨胀，也让帧级测试与业务级测试彼此独立。

### 20. 把 payload 复制到输出缓冲区后，为什么必须同步推进写入位置 `pos`？

**参考答案：**

`pos` 表示下一个待写字节的位置。复制 payload 后如果不执行 `pos += payload_len`，后续 CRC 会从 payload 起始位置写入，覆盖 payload 的前两个字节；空 payload 因长度为 0 可能碰巧通过，从而掩盖这个错误。START 等非空 payload 的精确字节测试能够暴露该问题。

### 21. 调用 CRC 函数时，起始指针和长度应该如何确定？

**参考答案：**

协议规定 CRC 覆盖 `version + command + payload_len + payload`。完整缓冲区中 version 位于偏移 2，因此起始指针应指向 `bytes.data() + 2`，长度为 `4 + payload_len`。不能从 `bytes.data()`开始，也不能把 magic 或尚未写入的帧尾 CRC 空间纳入计算。

### 22. 为什么在 C++17 中不能直接写 `ProtocolCodec::encode(frame) == EncodeResult{}`？

**参考答案：**

自定义结构体不会在 C++17 中自动生成 `operator==`，而 `EncodeResult` 也没有手写比较运算符，因此该表达式无法编译。测试应分别检查语义，例如先保存结果，再使用 `REQUIRE(result.ok())` 和 `REQUIRE(result.bytes == expected)`。即使定义结构体整体相等，拿成功结果与默认的空结果比较也不能验证正确编码出的帧内容。

## 项目协作｜新会话交接

### 23. 为什么要把 `AGENTS.md` 与 `PROJECT_PROGRESS.md` 分开？

**参考答案：**

`AGENTS.md` 保存长期稳定、需要每次会话遵守的规则，例如导学方式、测试授权和文档优先级；`PROJECT_PROGRESS.md` 保存会频繁变化的当前阶段、验证证据、已知问题和下一步。分开后，稳定规则不会被进度细节淹没，也能避免旧阶段状态长期留在自动加载的指令中。

### 24. 为什么新会话读取 `PROJECT_PROGRESS.md` 后，仍然必须检查 Git 和实际文件？

**参考答案：**

进度文档只是某个时间点的人工摘要，可能尚未记录用户刚完成的编辑、暂存区变化或最新测试结果。Git 状态、diff、实际文件和真实测试输出才是当前事实。新会话先读摘要用于快速定位，再用这些证据核对，可以避免重复工作、覆盖未提交修改，或把“已经写入”误报为“已经验证”。

## W1/S4｜ProtocolCodec 编码审查

### 25. 为什么 payload 为空、复制长度为 0 时，仍不应无条件调用 `std::memcpy`？

**参考答案：**

空 `std::vector` 的 `data()` 允许返回空指针，而 `std::memcpy` 要求传入有效指针；不能把“复制 0 字节”当成空指针一定合法。HELLO 和 STOP 都有合法空 payload，因此编码器应仅在 `payload_len > 0` 时调用 `std::memcpy`，随后再统一推进写入位置。

### 26. 为什么 UnsupportedVersion 测试还应把 command 设置为一个合法命令？

**参考答案：**

一个测试最好只引入一个导致失败的条件。若版本非法且 command 仍为默认 `Invalid`，结果会依赖编码器先检查哪个字段；测试实际上锁定了错误检查顺序，而不是单独证明“不支持的版本会被拒绝”。把 command 设为 `Command::Hello` 后，失败原因才唯一来自 version。

### 27. 为什么只判断 `frame.command == Command::Invalid` 仍不能阻止未知命令被编码？

**参考答案：**

`enum class` 能防止普通整数被隐式赋值，但调用方仍可通过 `static_cast<Command>(0x55)` 构造一个枚举声明中不存在的值。只排除 `Invalid(0x00)` 会让该未知值被原样写入线上帧。编码器应明确接受当前协议定义的命令集合，其余未定义或预留值统一返回 `InvalidCommand`。

### 28. `std::vector<std::uint8_t>` 的 `operator==` 会比较什么？

**参考答案：**

它比较两个 vector 的元素数量以及每个对应位置的元素，只有长度相同且全部元素按顺序相等时结果才为真。因此 `result.bytes == expected` 可以验证完整帧的总长度、字节顺序和每个字节的值。

### 29. 在精确示例测试中，为什么 `result.bytes == expected` 后通常不必再单独断言长度？

**参考答案：**

vector 相等本身已经要求长度相同。如果实际结果多一个或少一个字节，相等比较就会失败。单独检查长度只有在希望把“长度错误”和“内容错误”分别报告，或者测试本身只关心长度边界时才有额外价值。

### 30. 为什么 `payload_len` 可以使用 `std::uint16_t`，而 `total_len` 和 `pos` 更适合使用 `std::size_t`？

**参考答案：**

`payload_len` 对应协议中固定的 2 字节无符号字段，使用 `std::uint16_t` 能表达其线上宽度。`total_len` 和 `pos` 用于表示 C++ 容器的大小与下标，应与 `vector::size()` 的类型一致，使用 `std::size_t` 可以避免有符号/无符号混用和不必要的窄化转换。

### 31. 为什么错误路径除了检查错误码，还应检查 `result.bytes.empty()`？

**参考答案：**

错误码证明编码器识别了非法输入，而空输出证明它没有同时泄漏一段不完整或不可发送的帧。两项一起断言，才能锁定“失败时不产生线上数据”的接口契约。

### 32. 为什么 4096B 边界测试还要检查编码后的长度字段和 payload 首尾字节？

**参考答案：**

只检查输出总长 4104B，无法证明 `payload_len` 被正确写成小端 `00 10`，也无法证明整个 payload 被放在正确位置。增加长度字段及 payload 首尾检查，可以更有针对性地发现端序错误、偏移错误或边界处漏写数据。

### 33. 为什么本次既要确认构建成功，又要确认测试成功？

**参考答案：**

构建成功只证明当前源码能够完成编译和链接，例如标准库头、类型名称和函数声明没有阻止生成程序；测试成功才进一步证明程序在已覆盖场景中的行为符合预期。测试程序无法生成时谈不上执行，能生成也不代表编码逻辑一定正确，因此两种证据缺一不可。

### 34. 为什么构建日志中重新出现 `protocol_codec.cpp` 和 `test_protocol_codec.cpp` 很重要？

**参考答案：**

这证明刚修改的实现和测试实际参与了本次编译，运行的不是修改前遗留的旧测试程序。只有重新编译、重新链接后得到的可执行程序，其测试结果才能作为当前工作区的验证证据。

### 35. 12 个测试用例、43 个断言全部通过，为什么还不能说明 `decode()` 已经完成？

**参考答案：**

测试结论只覆盖本次实际编译和执行到的功能。当前新增用例验证的是 encode，已有用例验证 Frame 和 CRC；`decode()` 尚未实现，也没有对应测试。通过数量不能替代覆盖范围分析，因此只能宣布 encode 里程碑通过，不能把后续功能一并视为完成。

### 36. 为什么 VS2022 Debug 测试通过，仍不能替代项目默认的 VS2019 RelWithDebInfo 验收？

**参考答案：**

不同编译器版本和构建配置可能暴露不同的问题，例如标准库实现差异、警告与优化行为、宏定义以及只在优化后出现的未定义行为。VS2022 Debug 通过是有价值的补充证据，但项目声明的默认交付环境是 VS2019 RelWithDebInfo，因此最终阶段结论必须包含默认环境的实际构建和测试结果。

### 37. 为什么项目可以同时使用“VS2019 工具链”和“Ninja 生成器”？

**参考答案：**

编译器工具链负责把 C++ 源码编译、链接成程序，本项目当前使用 VS2019 提供的 `cl.exe`；CMake 生成器负责生成并驱动构建规则，当前使用 Ninja。Ninja 可以调用 VS2019 的编译器，因此两者描述的是构建链的不同层次，并不冲突。

### 38. 新会话能够读取根目录 `AGENTS.md`，为什么仍建议发送新会话启动指令？

**参考答案：**

`AGENTS.md` 适合保存长期稳定的仓库规则；启动指令会明确要求新会话读取动态的 `PROJECT_PROGRESS.md`、核对 Git 和实际工具链，并指出当前唯一任务。两者配合既避免把易过期的进度塞进长期规则，也能让新会话快速恢复到正确阶段。

## 项目协作｜默认环境复验前核对

### 39. 为什么不能仅凭目录名 `cmake-build-relwithdebinfo` 判断默认构建环境？

**参考答案：**

目录名只是人为约定，可以被误命名、复制或保留旧配置；真正决定构建行为的是目录内的 CMake 缓存和编译器识别结果。运行前应核对 `CMAKE_BUILD_TYPE`、`CMAKE_GENERATOR`、`CMAKE_CXX_COMPILER` 以及编译器 ID/版本，才能确认当前目录实际使用的是 RelWithDebInfo、Ninja 和预期的 MSVC 工具链。

### 40. `git status` 中新文件显示 `AM` 时，为什么必须同时查看 `git diff` 和 `git diff --cached`？

**参考答案：**

`AM` 表示该新文件已经有一个版本进入暂存区，同时工作区又在暂存版本之上继续修改。`git diff --cached` 显示暂存区相对 HEAD 的内容，`git diff` 显示工作区相对暂存区的内容；只看其中一个会漏掉另一层变化，可能误判实际实现或在后续操作中覆盖用户工作。

### 41. CMake 缓存确认了 VS2019、Ninja 和 RelWithDebInfo，为什么仍不能说当前 encode 已在默认环境通过？

**参考答案：**

CMake 缓存只能证明该构建目录配置为这些工具和构建类型，不能证明最新源码已经被重新编译，更不能证明测试已经执行成功。只有在当前工作区上实际构建目标，并运行 CTest 与测试可执行程序、记录真实输出后，才能把 encode 标记为已在默认环境验证。

### 42. `ninja: no work to do` 表示什么，为什么不能把它写成“本次重新编译了源码”？

它表示 Ninja 根据当前依赖图、输入和产物状态判断目标已经是最新的，因此构建命令成功但没有执行新的编译或链接动作。这可以作为目标未过期的证据，却不能伪装成本次日志中重新出现了编译步骤；应如实记录 `no work to do`，并结合已有 Ninja 构建记录、目标命令和随后实际运行的测试判断当前产物。

## W1/S4｜ProtocolCodec 解码设计

### 44. 为什么完整帧 `decode()` 不应该负责在缓存中搜索 magic、保留半包或消费字节？

**参考答案：**

这些操作依赖连续多次网络输入和缓冲区状态，属于流式 `StreamParser` 的职责。完整帧 `decode()` 应只校验并转换调用方交给它的一帧精确字节，使它保持无状态、输入输出清晰且容易单测。未来 StreamParser 负责找 magic、读取声明长度、等待整帧和重同步，然后把切出的单帧交给 decode。

### 45. 只读解码时，为什么参数通常应使用 `const std::vector<std::uint8_t>&`，而不是按值接收 vector？

**参考答案：**

按值接收会复制整个 vector，而解码只需要读取输入，并不需要拥有或修改它。使用常量引用可以避免最多 4104B 的无意义复制，同时通过类型约束表达“函数不会修改调用方字节”。如果以后需要支持任意连续内存，可再考虑指针加长度或 C++20 的 `std::span`，但当前 C++17 下常量引用足够清晰。

### 46. 为什么 `DecodeResult` 默认 `error=None` 容易造成失败开放？

**参考答案：**

只要某条尚未完成或遗漏的分支直接返回默认构造的结果，`ok()` 就会报告成功，即使 `frame` 仍是默认的 `Command::Invalid`。当前骨架在 magic 正确且长度至少 6B 时正会出现这种情况。解码器应采用失败关闭的默认状态，或确保只有完成所有长度、CRC、版本和命令校验并构造 Frame 后，才显式产生 `None` 成功结果。

### 47. 测试非法版本或未知命令时，为什么要重新计算一个正确的 CRC？

**参考答案：**

如果只修改版本或命令字而保留旧 CRC，帧同时具有 CRC 错误和语义错误，解码器可能会先正确返回 `CrcMismatch`，测试便无法单独证明版本或命令校验。重新计算正确 CRC 后，帧只保留目标无效条件，才能稳定验证 `UnsupportedVersion` 或 `InvalidCommand`。

### 48. 为什么最大 payload 的 encode/decode round-trip 不能替代协议文档中的固定示例测试？

**参考答案：**

如果 encode 和 decode 对同一个字段采用了相同的错误规则，两者可能互相抵消，使 round-trip 仍然通过。协议文档中的 HELLO、START 固定字节帧提供独立的外部基准；round-trip 适合验证双向一致性和 4096B 边界，但必须与固定向量测试配合。

### 49. 为什么解码失败测试还要确认返回的 `Frame` 保持默认无效状态？

**参考答案：**

错误码说明输入不可接受，而默认无效 Frame 可以防止调用方误用只解析了一部分、尚未通过 CRC 或语义校验的数据。只有全部校验完成后才暴露有效 Frame，能把“错误结果”和“可信业务数据”明确分开。

### 50. 小端的 `payload_len` 应如何从 `bytes[4]` 和 `bytes[5]` 还原？

**参考答案：**

`bytes[4]` 是低字节，应直接放在低 8 位；`bytes[5]` 是高字节，应先转换为足够宽的无符号类型再左移 8 位，最后按位或组合，即语义上为 `bytes[4] | (bytes[5] << 8)`。若写成 `bytes[4] << 8 | bytes[5]`，就按大端解释了，例如线上 `05 00` 会被误读成 1280 而不是 5。

### 51. 为什么复制解码后的 payload 前必须先调整 vector 大小，而且源偏移应为 6？

**参考答案：**

默认构造的 `frame.payload` 大小为 0，没有可供写入的元素；直接向其 `data()` 复制非零字节会写入无效存储。应先 resize 或按迭代器范围赋值。线上 payload 从完整帧偏移 6 开始，偏移 4 和 5 是 `payload_len`，从偏移 4 复制会把长度字段误当成 payload。payload 为空时应跳过 `memcpy`。

### 52. 解码时 CRC 的读取字节序和计算覆盖范围分别是什么？

**参考答案：**

帧尾 CRC 按小端存储，因此偏移 `6 + payload_len` 是低字节，下一字节是高字节。重新计算时必须从完整帧偏移 2 的 version 开始，覆盖 `version + command + payload_len + payload`，总长度为 `4 + payload_len`；不能只对 payload 计算，也不能把 magic 或帧尾 CRC 纳入范围。

### 53. 为什么读出 `payload_len` 后必须先检查 4096B 上限，再判断完整帧是否收齐？

**参考答案：**

超过 4096B 的声明本身已经违反协议，不应继续信任该长度或等待攻击者承诺的大块 payload。先检查上限可以立即返回 `PayloadTooLarge`，让未来 StreamParser 从当前候选 magic 滑动一个字节重新同步；若先检查完整长度，4097B 头会被误判成普通半包并长期占用缓存。

### 54. 精确单帧 decode 为什么既要检查输入小于预期长度，也要检查输入大于预期长度？

**参考答案：**

输入小于 `8 + payload_len` 表示帧尚不完整，应返回 `IncompleteFrame`；输入大于该长度表示调用方传入了尾随数据或多帧粘连，不符合“只解一帧精确字节”的接口契约，应返回 `FrameSizeMismatch`。只有大小完全相等，后续 CRC 偏移和 payload 边界才具有唯一含义。

### 55. 为什么完整帧结构确定后，通常先校验 CRC，再判断版本和命令是否合法？

**参考答案：**

版本和命令字也位于 CRC 覆盖范围内。如果传输损坏改变了这些字节但 CRC 未同步变化，先做语义判断会把损坏帧误报成版本或命令错误。先通过 CRC 确认受保护字节整体一致，再对具有正确 CRC 的帧返回 `UnsupportedVersion` 或 `InvalidCommand`，错误分类更可靠。

### 56. 核心代码注释为什么应优先解释设计意图和约束，而不是逐行翻译语法？

**参考答案：**

代码本身已经能表达赋值、判断和循环等“做了什么”，逐行翻译容易形成噪声，并可能在代码修改后变得过时。高价值注释应记录代码难以自行表达的原因、协议约束、职责边界和安全不变量，例如为什么超长长度必须立即拒绝、CRC 覆盖哪些字节，以及为什么失败时不能暴露部分 Frame。

### 57. 为什么要在 `decode()` 接口旁明确写出“只接受一帧精确字节”？

**参考答案：**

这句话定义了调用方与解码器的边界：输入不足返回 `IncompleteFrame`，输入有尾随字节返回 `FrameSizeMismatch`；找 magic、等待半包、拆分粘包和消费缓存则由 StreamParser 负责。若接口没有明确该契约，后续调用者可能把多帧缓冲直接交给 decode，或者让 decode 重复承担流式状态管理。

### 58. 为什么要注明解码失败时 `DecodeResult::frame` 必须保持默认无效状态？

**参考答案：**

长度、CRC、版本或命令任一校验失败时，已经读取出的字段都不应被业务层信任。让失败结果保持默认 `Command::Invalid` 和空 payload，可以防止调用方误用部分解析数据；只有全部校验通过后，才把完整 Frame 发布到结果中。

### 59. 为什么要遍历测试 0～5B 的每一种输入长度，而不只测试空输入？

**参考答案：**

固定帧头需要 6B，0～5B 的每个长度都处于“尚不能安全读取完整头部”的边界区间。逐一测试可以证明解码器在任一截断位置都会先返回 `IncompleteFrame`，不会因为已经存在部分 magic、version 或长度字节就越界读取后续字段。

### 60. 为什么 `Command::Invalid(0x00)` 和未知值 `0x55` 都需要独立的解码测试？

**参考答案：**

`Invalid(0x00)` 是枚举中声明的本地默认值，`0x55` 则是枚举声明之外的未知线上值。编码端必须拒绝二者，但 CRC 和长度正确的接收帧需要由 decode 保留原始命令值并交给业务层响应 `UNKNOWN_CMD`。分别测试可以防止 decode 把“已声明但不可发送”和“未声明值”中的任一类错误地当作结构损坏帧丢弃。

### 61. 为什么篡改非空 payload 后保留原 CRC，能够验证 CRC 的覆盖范围？

**参考答案：**

若 CRC 确实覆盖 payload，改变其中任一字节而不更新帧尾 CRC，就会使重新计算值与线上值不一致并返回 `CrcMismatch`。这项测试可以发现“只校验帧头”或“CRC 长度没有包含完整 payload”等覆盖范围错误，同时确认失败结果不会暴露被篡改的数据。

### 62. StreamParser 在缓存中找不到完整 magic 时，为什么仍要保留最后一个 `0xA5`？

**参考答案：**

最后一个 `0xA5` 可能是跨两次接收被拆开的 magic 首字节，下一批数据的第一个字节可能正是 `0x5A`。若把它与前面的噪声一起丢弃，就会漏掉一个合法帧；其他不可能成为 magic 前缀的字节则可以安全丢弃。

### 63. 候选帧出现超长 `payload_len` 或 decode 失败时，为什么只从候选 magic 起丢弃 1B，而不按声明长度或整段候选帧丢弃？

**参考答案：**

当前 magic 可能只是噪声中的伪起点，未经验证的长度也不可信；其后字节中可能已经包含另一个合法 magic。只滑动 1B 后重新搜索，可以避免被恶意或损坏的长度字段带偏，并遵守协议冻结的统一重同步规则。对当前无自重叠的 `A5 5A` 而言，滑动 2B 也不会漏掉 magic，但按声明长度、固定头长或整段候选跳过仍可能越过后方合法帧。

### 64. 为什么 CRC 正确但命令未知的完整帧不能被 StreamParser 当作损坏帧滑动 1B 重同步？

**参考答案：**

它的长度和 CRC 都已经证明帧边界完整可信，未知命令只是业务语义问题。StreamParser 应消费整个完整帧并把原始命令值交给业务层，业务层才能按协议回 `ERROR(UNKNOWN_CMD)`；若滑动 1B，会把一个结构合法的帧误当噪声，还可能在其 payload 内误找 magic。

### 65. 为什么 `feed()` 收到不足 6B 的 chunk 时不能直接返回，而必须先把它追加到内部缓存？

**参考答案：**

TCP 的一次接收可能只包含帧的一小部分，甚至每次只有 1B。当前 chunk 不足 6B 只表示“本次数据不够”，并不表示这些字节无效；必须先追加到跨调用保存的 `buffer_`，再根据整个缓存判断是否能继续，否则分多次到达的 magic、帧头和 payload 都会被丢失。

### 66. 为什么检查 `buffer[0]` 和 `buffer[1]` 不能替代在缓存中搜索完整的 `A5 5A`？

**参考答案：**

合法帧前可能存在任意数量的噪声，而且噪声末尾可能包含多个 `0xA5`。例如 `A5 A5 5A ...` 中第二个 `A5` 才是真正的 magic 起点；若看到第二字节不是 `0x5A` 就一次丢掉前两个字节，会把合法起点一起丢掉。搜索完整二字节序列并按其位置消费前缀，才能正确重同步。

### 67. 为什么 StreamParser 应把精确候选帧交给 `ProtocolCodec::decode()`，而不应再次自行判断版本、命令和 CRC？

**参考答案：**

CRC 和完整帧结构已经由 `ProtocolCodec::decode()` 统一定义，解析器重复实现会产生两套可能不一致的规则。StreamParser 只负责确定候选边界和缓存消费；decode 成功后，即使版本或命令未知，也应把保留原始值的 Frame 交给业务层处理。只有结构或 CRC 解码失败时，解析器才滑动 1B 重同步。

### 68. 候选帧尚未收齐时，为什么解析循环必须返回或跳出，而不能直接 `continue`？

**参考答案：**

候选帧未收齐时缓存没有任何字节被消费，当前调用也没有新数据可以追加。若立即 `continue`，下一轮仍会看到完全相同的缓存和长度条件，形成无限空转。应保留缓存并结束本次解析，等待下一次 `feed()` 带来更多字节。

### 69. 成功解析一帧后，为什么必须消费精确的 `frame_size` 并继续循环？

**参考答案：**

消费少了会把当前帧的尾部误当成下一帧噪声，消费多了会破坏后续粘连帧。只移除已经通过 decode 的精确帧长，才能保持下一字节仍是未处理输入；继续循环则可以在一次 `feed()` 中返回所有已经完整的 0～N 帧。

### 70. 为什么一个最大合法帧为 4104B 的协议，解析循环结束后保留的不完整候选最多只能是 4103B？

**参考答案：**

当合法长度字段最大为 4096B 时，完整帧总长最大是 `8 + 4096 = 4104B`。缓存达到 4104B 就不再是不完整候选：它必须被 decode 成功消费，或因结构/CRC 错误滑动重同步。因此只有少于完整最大帧的 4103B 才可能作为合法但尚未收齐的候选保留。

### 71. 为什么 Git 工作区干净、`main` 与 `origin/main` 一致，仍不能证明当前代码已通过默认环境测试？

**参考答案：**

Git 状态只说明已跟踪内容与当前提交一致、当前分支与远端跟踪分支没有可见差异；它不记录这份提交是否在指定工具链和配置下成功构建或测试。默认环境是否通过，必须由该提交对应的真实构建和测试命令及输出证明。

### 72. 为什么确认默认构建环境时必须读取 `CMakeCache.txt`，不能只根据 `cmake-build-relwithdebinfo` 目录名判断？

**参考答案：**

目录名只是人为命名，不会约束其中实际使用的生成器、编译器或构建类型。`CMakeCache.txt` 才记录该构建树配置时选定的 `CMAKE_GENERATOR`、`CMAKE_CXX_COMPILER` 和 `CMAKE_BUILD_TYPE`；结合编译器识别文件还能确认实际 MSVC 版本，避免把其他工具链的结果误当作默认环境验收。

### 73. 为什么目前不能把 `stream_parser.h` 已提交理解为 `StreamParser` 已实现或至少已被编译器验证？

**参考答案：**

该头文件目前只有接口和伪代码，`protocol/src/stream_parser.cpp` 尚不存在，`protocol/CMakeLists.txt` 也没有把 StreamParser 源文件加入 `protocol` 目标。现有目标不一定包含或实例化这个声明，因此历史构建结果既不能证明三个成员函数已有定义，也不能证明后续实现能够链接和满足流式解析契约。

### 74. 为什么对 `buffer_` 调用 `erase()` 后，不能继续使用此前由 `std::search()` 返回的迭代器？

**参考答案：**

`std::vector` 在删除元素后会使删除位置及其后的迭代器失效，移动元素或重新分配存储时还可能影响更多引用和指针。解析循环每次消费或滑动缓存后都应回到循环顶部重新搜索，不能拿旧迭代器继续计算位置或访问数据。

### 75. 为什么 `payload_len` 的高字节应先转换成足够宽的无符号类型，再左移 8 位？

**参考答案：**

`std::uint8_t` 参与算术时会先发生整数提升；显式转换为 `std::uint16_t` 后再左移，能清楚表达无符号小端组合的意图，避免代码依赖较窄类型、符号扩展或隐式提升规则。最终再与低字节按位或，得到协议规定的 16 位长度。

### 76. 为什么当前实现可以先使用 `vector::erase()` 消费缓存，而不必立即设计环形缓冲或维护复杂游标？

**参考答案：**

当前协议把单帧限制在 4104B，解析器正常结束时的不完整候选最多 4103B，数据规模有限。直接 `erase()` 虽会移动后续字节，但实现简单、边界清晰，足以先验证正确性；只有后续压测证明移动成本成为瓶颈时，才有证据引入读游标、批量压缩或环形缓冲。

### 77. 在缓存中找到 magic 且位置大于 0 后，为什么必须先丢弃 magic 前的噪声，才能读取 `buffer_[4]` 和 `buffer_[5]`？

**参考答案：**

帧字段偏移都是相对于 magic 起点定义的，只有当 magic 已经位于 `buffer_[0]` 时，索引 4 和 5 才是当前候选帧的 `payload_len`。若保留前缀噪声却直接读取固定索引，读到的只是噪声或其他字段；错误长度可能让解析器误判候选帧未收齐，即使后方已有完整合法帧也会停止解析。

### 78. 为什么“清空末尾不是 `0xA5` 的全部噪声”虽然不会漏掉 magic，却仍与当前冻结的 StreamParser 契约不一致？

**参考答案：**

从纯解析正确性看，末尾不是 `0xA5` 时确实不可能与下一批首字节组成 magic；但权威协议和头文件伪代码目前明确规定“找不到 magic 时保留最后 1B”。`buffered_size()` 会让缓存状态成为可观察行为，测试和调用方可能依赖这一契约。若要采用更激进的清空策略，应先统一修改协议、伪代码与测试，而不是只在实现中静默改变。

### 79. 为什么 `payload_len` 和 `frame_size` 最好分别显式声明为 `std::uint16_t` 与 `std::size_t`，而不是都用 `auto`？

**参考答案：**

按位运算的操作数会发生整数提升，因此两个看似为 `std::uint16_t` 的表达式经过 `|` 后，`auto` 可能推导为 `int`。显式类型既记录线上长度字段与容器大小的不同语义，也避免后续在与 `vector::size()`、迭代器偏移比较时发生不明显的有符号/无符号转换。

### 80. 为什么“找到 magic”的判断应是 `magic_idx + 1 < buffer_.size()`，而找不到时才是相反条件？

**参考答案：**

magic 需要当前位置和下一位置两个有效字节，因此只有 `magic_idx + 1` 仍落在容器范围内时，循环才可能在匹配处提前结束。若循环一直走到 `magic_idx + 1 >= size`，说明所有可检查的二字节窗口都不匹配；把条件写反会把成功匹配当成失败，或者在 magic 已位于索引 0 时反复执行空区间删除并无限循环。

### 81. 删除 magic 前缀后，为什么当前实现可以直接继续读取帧头，而不必无条件 `continue`？

**参考答案：**

删除范围精确截止到 magic 起点，删除后 magic 已位于 `buffer_[0]`；代码没有保留或继续使用删除前的迭代器，只使用新的容器大小和固定索引，因此可以立即检查 6B 帧头。重新进入循环也正确，但会重复一次搜索；关键是不能继续使用已经失效的迭代器。

### 82. 为什么把成功解码的 `result.frame` 移入结果数组，比再次复制它更合适？

**参考答案：**

`DecodeResult` 在本轮循环后不再使用，而 `Frame` 内含可能达到 4096B 的 payload。使用 `std::move` 可以把 payload 的动态存储所有权转交给结果数组，通常只需移动容器内部状态，避免再复制一份载荷；移动后不应继续依赖原 `result.frame` 的内容。

### 83. 非法长度候选后面紧跟合法帧时，如果按照非法 `payload_len` 跳过数据，会造成什么后果？

**参考答案：**

非法长度来自尚未通过验证的伪候选头，不能代表真实帧边界。按照它跳过数据可能跨过后方真正的 `A5 5A`，把完整合法帧连同噪声一起删除；解析器随后无法恢复这帧。只滑动 1B 并重新搜索，才能保留所有可能的后续起点。

### 84. StreamParser 在什么条件下才可以一次消费完整的 `frame_size`？

**参考答案：**

只有缓存已经包含 `frame_size` 个字节，并且这段精确候选通过 `ProtocolCodec::decode()` 的结构与 CRC 校验后，当前帧边界才可信。此时才能消费完整帧长；超长长度或 decode 失败时都只能滑动 1B 重新同步。

### 85. 对当前 magic `A5 5A`，为什么滑动 2B 不会漏掉一个从索引 1 开始的新 magic？

**参考答案：**

新 magic 的首字节必须是 `A5`，但当前已确认的索引 1 是 `5A`，所以索引 1 不可能同时成为新 magic 的起点。下一个候选最早只能从索引 2 开始，删除前 2B 仍会保留它。

### 86. 既然滑动 2B 对当前 magic 也安全，为什么实现仍保持滑动 1B？

**参考答案：**

权威协议和冻结伪代码已经明确规定失败时滑动 1B；保持该实现可以让代码、文档和未来测试一致。1B 还是不依赖同步字自重叠性质的统一保守规则，而当前缓存只有几 KB，改成 2B 没有值得改变契约的性能收益。

### 87. 工业实现中，“逻辑上滑动 1B”为什么不等于“必须每次对 vector 执行一次 1B erase”？

**参考答案：**

滑动 1B 描述的是下一次同步搜索必须从当前候选起点之后开始，这是解析语义。实现可以维护读游标，或直接从偏移 1 一次搜索下一个 magic，最后批量删除确认无用的前缀；这样能得到相同解析结果，同时减少反复移动 vector 元素的成本。

### 88. 为什么当前 `vector::erase()` 实现适合 V1，却不一定适合高吞吐工业场景？

**参考答案：**

当前帧最大只有 4104B，直接删除的代码简单、边界清楚，便于先验证正确性。但 `vector::erase()` 会移动后续元素，连续噪声或大量坏帧可能产生重复搬移；高吞吐场景通常改用读游标、批量压缩或环形缓冲，并通过压测判断是否值得增加复杂度。

### 89. 除了重同步规则，一个可长期运行的工业流式解析器还需要哪些保护？

**参考答案：**

至少需要不完整帧超时、缓存和输入资源上限、连续坏帧与 CRC 错误计数、日志和连接处置策略，以及拆包、粘包、噪声、损坏帧和随机分片测试。这些保护分别约束等待时间、内存、CPU 消耗和故障可观测性。

### 90. StreamParser 测试为什么既要检查返回的 Frame，也要检查 `buffered_size()`？

**参考答案：**

返回值只能证明解析器对外产生了哪些帧，不能证明内部缓存是否精确消费。同步错误可能暂时返回正确 Frame，却遗留帧尾、重复数据或不该保留的噪声；同时检查 `buffered_size()` 才能验证半包被保留、成功帧被完整消费、reset 确实清空状态。

### 91. 第一批 StreamParser 测试为什么适合使用协议文档中的固定帧字节，而不是全部现场调用 `ProtocolCodec::encode()` 生成？

**参考答案：**

固定文档向量是独立的线上契约证据，不依赖被测程序中的编码实现。若所有输入都由同一套 codec 生成，编码和解析可能共享相同误解而让测试同时通过；先用已冻结的 HELLO、START 字节可以确认 StreamParser 面对真实协议序列的行为。

### 92. 逐字节喂入完整帧时，为什么除了检查最后成功，还要检查最后一字节到达前始终没有输出 Frame？

**参考答案：**

只检查最终成功无法发现解析器是否曾在帧未收齐时过早发布部分结果。每次前缀输入都应返回空结果并保留缓存，直到 CRC 的最后一个字节到达；这能验证 TCP 任意分片下的失败关闭和完整帧边界。

### 93. 两帧粘连测试为什么必须先断言 `frames.size() == 2`，不能只遍历实际返回的 frames？

**参考答案：**

遍历只会检查已经存在的元素；若解析器错误地返回 0 帧或 1 帧，缺少的分支根本不会执行。尤其当错误实现同时清空缓存时，测试可能没有任何失败断言。先锁定数量为 2，再检查索引 0 和 1 的内容，才能证明两帧都被解析且顺序正确。

### 94. 逐字节测试最后使用 `frames.size() > 0` 为什么不够严格？

**参考答案：**

该输入只有一帧，正确结果必须恰好为 1。`> 0` 会放过重复发布同一帧或产生额外伪帧的错误；使用 `== 1` 才同时验证没有漏帧和没有多帧，并保证后续访问 `frames[0]` 的契约清晰。

### 95. 遍历 vector 时为什么优先使用 `std::size_t` 而不是 `int` 作为索引？

**参考答案：**

`vector::size()` 返回无符号的 `std::size_t`，用 `int` 比较会发生有符号与无符号转换并可能触发警告；极大容器的大小还可能超出 `int`。使用 `std::size_t` 能与容器接口保持一致，避免不必要的隐式转换。

### 96. 粘包测试中为什么还要再次检查 HELLO 的 payload 为空，不能只依赖单帧测试已经覆盖？

**参考答案：**

粘包场景需要独立证明第一帧的结束边界没有吞入第二帧字节。即使单独 HELLO 能得到空 payload，错误的粘包消费逻辑仍可能污染第一帧或错位第二帧；在该场景再次检查 payload，能让测试独立验证边界和顺序。

### 97. 测试源文件为什么应显式包含自己直接使用的标准库头，而不依赖被测头文件的间接包含？

**参考答案：**

间接包含是被测头文件的实现细节，未来它移除某个 include 后，测试可能无缘无故失去类型声明。显式包含 `<cstddef>`、`<cstdint>` 和 `<vector>` 能准确表达当前文件的依赖，使编译关系稳定且便于审查。

### 98. 为什么测试代码通过静态审查后仍只能记录为“已实现但未验证”？

**参考答案：**

静态审查只能检查可见的逻辑、边界和断言设计，不能证明代码能够在目标工具链编译、链接，也不能证明运行时结果符合预期。只有实际构建并执行测试得到成功输出后，才能把对应范围移入“已验证”。

### 99. 噪声前缀测试为什么适合在合法 HELLO 前放置一个额外的 `0xA5`，而不只使用普通的 `0x00`？

**参考答案：**

单独的 `0xA5` 是 magic 的首字节，能构造 `A5 A5 5A` 这种重叠搜索边界。解析器必须拒绝第一个不完整匹配，并从第二个 `A5` 识别真正的 `A5 5A`；只用 `0x00` 只能覆盖容易跳过的普通噪声。

### 100. CRC 错帧恢复测试为什么要在坏帧后紧接一个完整合法帧？

**参考答案：**

只输入 CRC 错帧只能证明没有发布坏数据，不能证明滑动重同步正确。紧接合法帧并断言只返回该合法帧，可以同时验证坏候选未泄漏、失败后没有清空过多数据、后续 magic 能被重新找到且缓存最终被正确消费。

### 101. 超长长度恢复测试为什么只需要构造 6B 非法帧头，不需要真的附加 4097B payload？

**参考答案：**

协议要求读取完整 6B 头后立即检查 `payload_len` 上限；4097 已经确定非法，解析器不得等待或信任对应 payload。只给非法头并紧接合法帧，正好能证明它立即滑动重同步，而不是把非法长度误当成普通半包长期等待。

### 102. CRC 错误测试为什么适合从已知合法帧复制后只翻转一个 CRC 位，而不是手写一组任意的坏字节？

**参考答案：**

从合法帧只改变 CRC，可以保证 magic、长度、命令和 payload 仍然只有一个失败条件，测试失败原因唯一指向 CRC。手写任意坏字节可能同时破坏长度或结构，使测试实际走到其他错误分支，无法证明 CRC 失败后的重同步行为。

### 103. CRC 错帧后恢复出的 START 为什么必须检查完整 payload，不能只检查命令？

**参考答案：**

命令正确只能证明解析器大致找到了后续帧，不能证明候选边界和 payload 截取完全正确。检查五字节 START payload 可以发现坏帧残留混入、起点偏移或长度消费错误，确保恢复后的 Frame 内容完整可信。

### 104. 为什么测试名称和标签应明确写出 CRC、length 与 resync，而不是笼统使用 bad 或 invalid？

**参考答案：**

明确名称能直接说明输入条件和期望行为，失败日志无需阅读实现即可定位场景；细分标签还允许 Catch2 按 CRC、长度或重同步筛选用例。`bad`、`invalid` 无法区分具体错误路径，会降低诊断和维护效率。

### 105. 最大帧 StreamParser 测试为什么可以使用 `ProtocolCodec::encode()` 生成输入，而不必手写 4104B 字节？

**参考答案：**

该测试关注的是 StreamParser 对最大合法帧的缓存和消费边界，不是在重新验证编码算法；ProtocolCodec 的 4096B 编码边界已有独立测试。使用 encode 可以可靠生成长度与 CRC 一致的合法帧，避免手写大量字节和 CRC 引入与本测试目标无关的错误。

### 106. 为什么最大合法帧的前 4103B 必须全部保留，而不能为了限制缓存提前丢弃一部分？

**参考答案：**

最大 payload 为 4096B，加上 8B 固定开销后完整帧是 4104B。前 4103B 仍可能只是缺少最后一个 CRC 字节的合法帧，解析器没有依据判错或消费；提前丢弃会破坏一个仍有可能完成的合法候选。

### 107. 为什么把最大帧最后 1B 单独喂入，比一次输入完整 4104B 更能发现边界错误？

**参考答案：**

分成 4103B 和 1B 可以同时验证最大半包被完整保存，以及从“不完整”到“恰好完整”的临界转换。一次输入完整帧只能验证成功路径，无法发现解析器在 4103B 时提前丢弃、错误消费或缓存上限少算 1B 的问题。

### 108. 最大帧测试为什么应在访问 `result.bytes.back()` 或构造迭代器区间前先使用 `REQUIRE(result.ok())`？

**参考答案：**

如果编码失败，`result.bytes` 按契约应为空，此时调用 `back()` 会产生未定义行为，使用 `end() - 1` 也不合法。Catch2 的 `REQUIRE` 失败后会终止当前测试段，因此先锁定编码成功，后续对字节数组的访问才有有效前置条件，失败也会停在真正的原因上。

### 109. 为什么静态审查确认了 4103B/4104B 断言完整，仍不能把 StreamParser 记为“已验证”？

**参考答案：**

静态审查只能说明测试设计和可见代码逻辑与协议契约一致，不能证明它们能在 VS2019 + RelWithDebInfo 下编译、链接并按预期运行。只有该提交对应的真实构建、CTest 和测试程序输出成功，才构成默认环境验收证据。

### 110. 为什么默认环境验收既要核对 `CMakeCache.txt`，又要记录实际构建与测试命令？

**参考答案：**

`CMakeCache.txt` 证明构建树配置的是 Ninja、RelWithDebInfo 和指定 MSVC，但不能证明当前提交已被重新编译或测试。实际命令及输出把工具链配置、目标构建和运行结果关联起来，避免把旧产物、其他生成器或 VS2022 Debug 的结果误当成默认环境验收。

### 111. 为什么“随机分片”测试应使用固定种子或固定分块序列，而不应每次依赖不可复现的真随机输入？

**参考答案：**

测试失败后必须能够用相同输入稳定复现和调试。固定种子或固定分块序列仍能覆盖不均匀边界，同时保证本地、CI 和后续回归可以重放同一案例；真正随机探索可以作为额外模糊测试，但不应替代可复现的基础单测。

### 112. 为什么多次调用 `feed()` 时要把每次返回的 Frame 累积起来，而不能只检查最后一次调用的返回值？

**参考答案：**

任意一个 chunk 都可能刚好补齐一帧，解析器会在当次调用立即返回它，而不是等到整个输入结束。只检查最后一次返回值会漏掉此前已经正确发布的帧，也无法验证发布顺序；累计全部返回结果才能重建这段字节流产生的完整帧序列。

### 113. 为什么应在合法帧的 payload 中主动放入 `A5 5A`，再进行非均匀分片测试？

**参考答案：**

magic 只应在寻找新候选起点或错误重同步时使用。合法帧边界由头部长度和 CRC 决定，payload 内出现相同字节不能被误当成新帧；把 `A5 5A` 放进 payload 能验证解析器在半包、跨 chunk 和粘包情况下仍按已声明长度收完整候选，而不是错误地从 payload 中间重新同步。

### 114. 分片循环为什么必须保证每次计算出的 `chunk_size` 大于 0？

**参考答案：**

循环依靠 `offset += chunk_size` 推进。如果允许零长度 chunk，`offset` 不变，循环条件会一直成立并形成无限循环。固定分块序列应只包含正数，同时最后一块只缩小到非零的剩余长度。

### 115. 为什么最后一个 chunk 要用 `min(requested_size, remaining)` 一类逻辑限制到剩余字节数？

**参考答案：**

固定分块大小不一定恰好整除输入总长度。若直接用请求大小计算结束迭代器，最后一次可能越过 `stream.end()`，构造 vector 时产生未定义行为；取请求大小与剩余长度中的较小值，可以安全地把最后所有字节恰好喂完。

### 116. 为什么分片测试不能只断言最终帧数，还要逐帧检查命令顺序与 payload？

**参考答案：**

帧数正确并不代表边界正确：解析器可能交换发布顺序、把相邻帧字节混入 payload，或在 payload 内的 magic 处错误切帧后碰巧仍产出相同数量。逐帧比较版本、命令和完整 payload，才能证明分片前后的字节流语义完全一致。

### 117. 为什么多个互不相关的源文件同时报 MSVC `C1902`，更可能是工具链环境问题，而不是新增测试的 C++ 逻辑错误？

**参考答案：**

`C1902` 指向编译器与程序数据库管理组件不匹配，发生在生成调试信息阶段。若协议实现、旧测试、Catch2 和新增测试等多个无关编译单元都以同一错误失败，且没有任何源码位置或 C++ 语法诊断，公共工具链组件比某一处业务代码更符合共同原因。

### 118. 为什么 VS2022 Debug 的 35 个用例、182 个断言通过，仍不能写成默认 VS2019 + RelWithDebInfo 已验收？

**参考答案：**

两者使用不同的编译器版本、运行库、优化级别和构建配置，可能暴露不同的兼容性或未定义行为。VS2022 结果能证明新增代码在补充环境中成功编译并运行，但项目明确把 VS2019 + RelWithDebInfo 定为默认门槛，因此默认环境仍需独立证据。

### 119. 遍历一帧的全部二段切分位置时，为什么每个切点都应创建新的 `StreamParser`？

**参考答案：**

每个切点都是一项独立场景。复用同一个解析器会让前一轮残留缓存或已消费状态影响下一轮，测试失败时也难以判断是哪一个切点造成。为每个切点创建全新实例，可以隔离状态并确保结果只由当前两段输入决定。

### 120. 为什么构建在编译阶段失败后，不应继续运行 CTest 并把结果当作本次修改的验证？

**参考答案：**

编译失败意味着新的测试源文件没有生成对应目标，磁盘上的测试程序仍可能是旧版本。即使随后 CTest 启动并显示旧程序通过，也只证明旧二进制的行为，不能覆盖本次修改；必须先成功重新构建当前源码，再运行测试。

### 121. 为什么多个互不相关的源文件都报同一个 MSVC `C1902`，更像工具链环境问题而不是某一段 C++ 代码错误？

**参考答案：**

`C1902` 明确指向编译器与程序数据库管理组件版本不匹配，而不是语法、类型或链接错误。当协议实现和多个独立测试源文件都在相同阶段统一失败，说明共同使用的 PDB 工具链组件存在问题；若是新增测试代码错误，通常只会在相关源文件产生具体 C++ 诊断。

### 122. 为什么不能用时间早于新增测试源文件的 `protocol_tests.exe` 验证当前测试？

**参考答案：**

较早生成的可执行文件不可能包含后来写入的测试代码。运行它得到的用例数和结果只对应旧源码版本，与当前工作区不一致；验收必须使用成功重新编译当前源文件后生成的新二进制。

### 123. 为什么 Visual Studio 多配置生成器构建时必须显式写 `--config RelWithDebInfo`？

**参考答案：**

多配置生成器在同一构建树中同时支持 Debug、Release、MinSizeRel 和 RelWithDebInfo，`CMAKE_BUILD_TYPE` 不负责选择本次要构建的配置。`--config RelWithDebInfo` 才会让 MSBuild 选择对应目标、编译选项和输出目录，避免误用默认或旧的 Debug 产物。

### 124. 哪些构建日志证据可以证明本次实际使用了 MSVC 2022 的 RelWithDebInfo，而不只是目录名称这样写？

**参考答案：**

缓存记录 Visual Studio 17 2022、x64 和 MSVC 19.38；实际命令调用 VS2022 的 MSBuild 与 14.38 工具集 `cl.exe`，并带有 `RelWithDebInfo` 配置、`/O2`、`/Zi`、`NDEBUG` 和 C++17 等参数，输出也落在 `build/.../RelWithDebInfo`。这些共同构成实际工具链与配置证据。

### 125. 默认环境切换后，为什么仍应保留旧 VS2019 `C1902` 的历史记录，但不再让它阻断主线？

**参考答案：**

历史记录能解释旧构建树为何失败，并防止以后误把同一环境问题当成源码回归；但验收门槛已经由用户明确改为 MSVC 2022 + RelWithDebInfo，而且当前代码在新默认环境完成了真实重编译和测试，因此旧工具链故障不再决定当前里程碑是否通过。

### 126. 为什么全部二段切点测试只遍历 `1` 到 `frame_size - 1`，不包含 `0` 和 `frame_size`？

**参考答案：**

切点 0 会让第一段为空、第二段包含完整帧；切点等于帧长则相反。两者都没有把帧真正拆成两个非空部分，不能检验半包缓存。内部切点 `1..frame_size-1` 才完整覆盖所有合法的二段拆分位置。

### 127. 第一段输入后为什么除了断言没有 Frame 输出，还要断言 `buffered_size() == split_pos`？

**参考答案：**

没有输出只能证明解析器暂时没有发布帧，不能证明它完整保留了合法前缀；错误实现可能静默丢失部分字节并同样返回空。缓存大小精确等于切点，能验证从单字节 magic 到只缺最后 CRC 字节的每种前缀都未被提前消费或丢弃。

### 128. 在切点循环中使用 `CAPTURE(split_pos)` 有什么诊断价值？

**参考答案：**

循环里的断言源码位置都相同；若没有上下文，失败日志只能指出某条 REQUIRE，无法知道是哪一个边界触发。`CAPTURE(split_pos)` 会把当前切点附加到 Catch2 失败输出，使 magic、帧头、payload 或 CRC 附近的失败可以立即定位和复现。

### 129. 为什么新增一个 Catch2 测试用例后，断言数会从 182 增加到 268，而不是只增加固定的几条？

**参考答案：**

该测试先执行 2 个编码前置断言，再对 12 个切点分别执行 7 个行为断言，因此实际增加 `2 + 12 × 7 = 86` 个断言。Catch2 按运行次数统计循环内断言，所以用例数只增加 1，断言数却从 182 增加到 268。

### 130. 构建日志显示其他目标“所有输出均为最新”，为什么本次结果仍能验证新增测试？

**参考答案：**

本次修改只涉及 `test_stream_parser.cpp`，日志明确显示该文件由当前 MSVC 14.38 以 RelWithDebInfo 参数重新编译，并重新链接生成 `protocol_tests.exe`。未变化的协议库和其他测试保持最新是正常的增量构建行为；关键是修改过的编译单元和最终可执行文件确实得到更新。

### 131. 全部二段切点测试证明了什么，又不能单独证明什么？

**参考答案：**

它证明同一合法非空帧在任意一个内部位置拆成两个非空 chunk 时，都能完整保留前缀并在补齐后恢复原帧。它不能单独覆盖多帧粘连、三段以上分片、噪声、CRC 错误或超长长度重同步；这些行为需要其他独立测试共同提供证据。

### 132. 为什么第一版 device_simulator 选择单线程阻塞 Winsock，而不立即使用异步框架或网络线程？

**参考答案：**

当前只要求一个客户端完成控制命令闭环，阻塞的 `accept` / `recv` 已能满足功能，并能直接学习 Socket 生命周期、断开语义和部分发送。异步回调、线程同步和队列会扩大当前目标，只有后续 DATA 推流或多连接需求证明阻塞模型不足时才值得引入。

### 133. 为什么一次 `recv()` 的返回数据必须直接交给 `StreamParser::feed()`，不能假设它恰好是一帧？

**参考答案：**

TCP 只提供有序字节流，不保留发送端每次 `send()` 的消息边界；一次 `recv()` 可能拿到半帧、一帧或多帧。`StreamParser` 已负责缓存半包、拆分粘包和错误重同步，因此网络层只应把实际收到的字节块交给它，而不能按 `recv` 次数推断帧边界。

### 134. 为什么发送一条编码后的协议帧时仍需要 `send_all()` 循环？

**参考答案：**

`send()` 成功只表示本次接受了返回值所示的字节数，不保证整段缓冲一次全部发送。若忽略部分发送，帧尾或后续 payload 可能丢失，客户端只能得到永久半包；`send_all()` 应持续推进偏移，直到全部字节提交或出现错误、连接关闭。

### 135. 为什么 `sockaddr_in::sin_port` 要使用 `htons()`，而 VirtualBenth 帧内的 `payload_len` 不能使用 `htons()`？

**参考答案：**

端口属于 TCP/IP 地址结构，必须使用网络字节序；`htons()` 正是把主机 16 位整数转换成该表示。VirtualBenth 帧字段则由应用层协议明确规定为小端，并由 `ProtocolCodec` 显式序列化；对其再调用 `htons()` 会把两个不同层次的字节序规则混在一起，导致双端解释不一致。

### 136. 为什么监听 Socket 和客户端 Socket 必须分别管理、分别关闭？

**参考答案：**

监听 Socket 只负责 `listen` 和 `accept`，客户端 Socket 才承载具体连接的 `recv` 与 `send`。关闭一个客户端连接不应终止监听；反过来，程序退出时只关闭监听句柄也会泄漏已接受的连接。两者拥有不同生命周期，因此需要独立句柄和清理路径。

### 137. 为什么每次 `accept()` 成功后都应为该连接创建新的 `StreamParser`？

**参考答案：**

`StreamParser` 内部保存尚未组成完整帧的字节，它属于某一条 TCP 字节流。若不同客户端复用同一个实例，上一个连接遗留的半个 magic、帧头或 payload 会与新连接的数据拼接，造成跨连接污染；连接结束时应销毁或重置其专属解析器。

### 138. 为什么 `WSAStartup()` 失败时应直接使用它的返回值，而不是调用 `WSAGetLastError()` 获取原因？

**参考答案：**

`WSAStartup()` 本身直接返回具体 Winsock 错误码，而且失败时 Winsock 运行时尚未成功初始化；此时没有必要依赖最近错误状态。其他多数 Winsock API 则用 `SOCKET_ERROR` 或 `INVALID_SOCKET` 表示失败，再通过 `WSAGetLastError()` 取得详细错误码。

### 139. `accept()` 成功后为什么会得到一个新的客户端 Socket，而不是直接使用监听 Socket 收发数据？

**参考答案：**

监听 Socket 表示本地监听端点，职责是维护等待队列并接受后续连接；`accept()` 返回的新 Socket 才代表与某个具体客户端建立的 TCP 连接。分离这两个句柄后，服务端可以在关闭某个会话时继续保留监听能力，也能为不同连接维护独立解析状态。

### 140. 为什么 `recv()` 和 `send()` 的缓冲区长度参数需要显式转换并保证不超过 `int` 上限？

**参考答案：**

STL 容器的大小使用 `std::size_t`，而 Winsock 的 `recv()` / `send()` 长度参数是 `int`。无条件窄化可能让超大长度截断或变成错误值，因此应先把单次请求限制到 `INT_MAX` 以内，再显式转换。当前帧最大只有 4104B，但通用发送循环仍应保留这个边界。

### 141. 为什么 `ProtocolCodec::encode()` 成功，仍不能证明空 payload 的 ACK、STATUS 或 ERROR 符合业务协议？

**参考答案：**

编码器负责把结构完整且可发送的 `Frame` 序列化，并不自动替业务层补齐每种命令的字段语义。权威协议另外规定 ACK payload 固定为 2B、STATUS 固定为 1B、ERROR 至少为 2B；因此业务层必须先按命令构造正确 payload，再检查编码结果。

### 142. 为什么 `for (const auto& frame : frames)` 内的 `break` 不能实现“发送错误后关闭当前连接”？

**参考答案：**

该 `break` 只退出最内层的帧遍历循环，外层 `while (true)` 随后仍会再次调用 `recv()`。若协议要求发送某类 ERROR 后关闭连接，应把连接处置结果传到外层，或从会话处理函数返回，确保发送完成后真正结束接收循环并关闭客户端 Socket。

### 143. 为什么首个本机联调版本优先绑定 loopback，而不是 `INADDR_ANY`？

**参考答案：**

`INADDR_ANY` 会在所有本机 IPv4 网卡上接受连接，使尚未完成输入验证和错误处理的实验服务暴露给局域网；loopback 只允许本机客户端访问，范围与当前“单机最小闭环”目标一致。需要跨机器联调时，再显式扩大监听范围并同时评估防火墙与安全边界。

### 144. 为什么给 `ackFrame.payload` 再次赋值，不能设置随后编码的 `statusFrame` payload？

**参考答案：**

`ackFrame` 和 `statusFrame` 是两个相互独立的对象，各自持有自己的 `payload` 容器。修改 `ackFrame.payload` 不会影响 `statusFrame`；随后对 `statusFrame` 编码时仍会得到空 payload。STATUS(READY) 必须显式执行 `statusFrame.payload = {0x01}`。

### 145. 为什么把监听 Socket 和客户端 Socket 包装为局部 RAII 对象，比只在 `run()` 末尾手动 `closesocket()` 更可靠？

**参考答案：**

`socket`、`bind`、`listen`、`accept`、`recv` 或 `send` 都可能触发提前返回，后续容器操作也可能抛出异常；只在函数末尾关闭会漏掉这些路径。局部 RAII 对象在离开作用域时自动析构，因此正常返回、错误返回和异常展开都会关闭其拥有的有效 Socket。

### 146. 为什么 `WSAStartup()` 成功但协商版本不是 2.2 时，需要在构造函数抛出异常前手动调用 `WSACleanup()`？

**参考答案：**

`WSAStartup()` 返回 0 已经增加了当前进程的 Winsock 初始化计数，之后发现版本不满足要求仍需撤销这次成功初始化。由于构造函数抛出后对象没有构造完成，其析构函数不会执行，所以必须在抛出前手动调用一次 `WSACleanup()`；如果 `WSAStartup()` 本身失败，则没有成功初始化需要清理。

### 147. 核心代码注释为什么应优先解释“为什么这样做”和“不变量”，而不是逐字复述赋值语句？

**参考答案：**

变量名和语句本身通常已经说明“做了什么”，逐字复述会增加阅读噪声，并可能在代码修改后变成误导。生命周期顺序、协议约束、端序、错误处置和 TCP 没有消息边界等原因无法仅从单行语句看出，注释记录这些设计理由和必须保持的不变量，才能帮助维护者安全修改代码。

### 148. 为什么 `SocketHandle`、`send_all()` 和帧处理辅助函数适合放在 `.cpp` 的匿名命名空间中？

**参考答案：**

这些类型和函数只服务于当前实现，不属于其他模块需要依赖的公开接口。匿名命名空间赋予它们内部链接，避免导出无关符号或与其他翻译单元重名；同时头文件无需暴露 `SOCKET` 和 `<winsock2.h>`，从而降低编译依赖并保留未来替换传输实现的空间。

### 149. `run()` 中为什么先声明 `listen_socket`、后声明 `client_socket`，这对自动清理顺序有什么影响？

**参考答案：**

同一作用域内的局部对象按构造顺序的逆序析构，所以后声明的 `client_socket` 会先关闭，随后才关闭 `listen_socket`。这样退出会话时先释放具体客户端连接，再停止监听，与二者的职责和依赖关系一致；无论正常返回、错误返回还是异常展开都保持相同顺序。

### 150. 为什么 NetAssist 可能一次显示连续的 ACK 和 STATUS 字节，而不是分成两条接收记录？

**参考答案：**

服务端虽然按顺序调用两次发送，但 TCP 只提供有序字节流，不保留每次 `send()` 的消息边界。网络栈可能把两个协议帧合并到一次接收中，也可能拆成多次显示；判断时应按帧头中的 `payload_len` 切分，而不能按 NetAssist 的接收记录行数判断帧数。

### 151. 为什么使用当前模拟器测试不同连接场景时，通常需要重新启动服务端？

**参考答案：**

当前 S7 是单客户端、单次 `accept()` 的最小实现：当前客户端正常断开或版本不匹配触发主动关闭后，`run()` 返回，进程随之退出。它还没有外层循环重新接受下一位客户端，因此每个独立连接场景都需要重新启动模拟器。

### 152. 在收到 `ERROR(UNKNOWN_CMD)` 后，同一连接继续发送合法 HELLO 有什么验证价值？

**参考答案：**

协议要求未知命令只返回 `UNKNOWN_CMD`，不关闭连接。随后在同一连接发送 HELLO 并收到正确 ACK 与 STATUS，既证明错误码正确，也证明服务端没有因未知命令退出、关闭 Socket 或破坏当前连接的解析状态。

### 153. 合法 HELLO 的 NetAssist 记录为什么恰好是 19B，如何从两个响应帧的结构计算出来？

**参考答案：**

每帧固定开销为 8B。ACK payload 固定 2B，所以 ACK 总长为 `8 + 2 = 10B`；STATUS payload 固定 1B，所以 STATUS 总长为 `8 + 1 = 9B`。TCP 把两帧合并到一次接收记录时，总长度就是 `10 + 9 = 19B`。

### 154. 版本不匹配场景中，收到正确 ERROR 后立即断开为什么是成功证据而不是通信故障？

**参考答案：**

权威协议明确规定版本不一致时发送 `ERROR(VER_MISMATCH)`，随后关闭连接，并且不能发送 ACK。日志先出现错误码 `0x0002` 的完整合法帧，再由服务端断开，顺序与连接处置都符合协议，因此属于预期成功路径。

### 155. 当前三条 NetAssist 日志仍不能证明哪些网络行为已经可靠？

**参考答案：**

它们证明正常 HELLO、版本错误、未知命令及连接处置，但没有强制触发 `send()` 部分发送、Winsock API 失败、客户端中途复位、接收超时或连续多客户端连接。人工发送通常也不能保证操作系统真的按指定位置拆包；这些行为仍需自动化测试、故障注入或后续可靠性阶段验证。

### 156. 为什么会话内部需要单独的 `AwaitHello` 状态，而不应直接复用协议中的 `IDLE` 状态？

**参考答案：**

`AwaitHello` 表示连接刚建立、握手尚未完成，是服务端内部的会话阶段；协议中的 `IDLE` 表示设备已经完成握手，并在停止采集后处于空闲状态。若把两者混为一谈，服务端就可能错误地允许客户端在发送 HELLO 前直接 START，也无法准确校验重复 HELLO 等非法状态转换。

### 157. 处理 START 时，为什么必须先确认 payload 恰好为 5 字节，再按小端序读取 `sample_rate`？

**参考答案：**

START 的线上格式固定为 4 字节小端 `sample_rate` 加 1 字节 `chan_mask`。先检查精确长度可以防止越界读取，也能拒绝带有未定义尾随字段的模糊报文；显式按小端序还可避免把主机字节序误当成协议字节序，使解析结果跨平台保持一致。

### 158. 为什么命令参数或会话状态非法时，既不能发送 ACK，也不能改变当前状态？

**参考答案：**

ACK 表示该命令已经成功执行；非法请求若仍发送 ACK，会让客户端误以为状态转换完成。错误请求也不应影响已有合法会话，因此应只发送对应的 `ERROR(BAD_PARAM)` 或 `ERROR(BAD_STATE)`，并保持原状态不变，客户端修正请求后才能继续从一致的状态重试。

## 项目梳理｜当前代码全流程图

### 159. 为什么完整的接收流程必须分成“TCP 字节块 → StreamParser → 精确单帧 decode → 业务分发”四层，而不能直接把每次 recv() 的结果交给业务层？

**参考答案：**

TCP 不保留发送边界，一次 recv() 可能得到半帧、一帧或多帧。StreamParser 需要跨调用缓存并完成定界、粘包拆分和错误重同步；ProtocolCodec::decode() 再对切出的精确单帧统一校验结构与 CRC；只有通过这些检查的 Frame 才能进入业务层。分层后每一层的状态和错误语义都清楚，也能分别测试。

### 160. 为什么当前 SessionState 不能直接通过 static_cast 转成 STATUS.state 发送到线上？

**参考答案：**

当前 SessionState 的隐式枚举值是 AwaitHello=0、Ready=1、Running=2、Idle=3，而协议规定 STATUS.state 为 IDLE=0、READY=1、RUNNING=2、FAULT=3。AwaitHello 是内部会话阶段，协议中没有对应状态；Idle 的当前值又会在线上被解释为 FAULT。因此内部状态与线上状态需要明确映射，不能依赖枚举声明顺序恰好一致。

### 161. 当前 send_hello_success() 先读取 sessionState_ 构造 STATUS，调用成功后才把状态改为 Ready，会产生什么可观察结果？

**参考答案：**

首次连接时 sessionState_ 仍是 AwaitHello，其隐式值为 0，所以函数会先发送 STATUS(0)，客户端按协议会把它解释为 IDLE；随后服务端才在内存中改为 Ready。这样线上通知与内部最终状态不一致，也不符合 HELLO 成功后应发送 STATUS(READY) 的契约。该路径必须修正并重新构建、测试和联调后才能验收。

### 162. 为什么在处理每一帧前只检查一个 `isRepeatHello` 布尔值，不能正确识别“重复 HELLO”？

**参考答案：**

布尔值只记录上一帧曾成功处理 HELLO，却没有说明当前帧的命令是什么。若成功 HELLO 后把它置为 true，那么下一帧即使是合法 START，也会被误判为重复 HELLO。重复 HELLO 应通过“当前命令确实是 HELLO，并且会话状态已经不是 AwaitHello”这一组合条件判断。

### 163. 为什么成功响应函数应显式接收目标 STATUS，而不应在状态转换前直接读取当前内部状态？

**参考答案：**

HELLO、START、STOP 成功后分别需要发送 READY、RUNNING、IDLE，这些是命令成功后的目标状态。转换前读取到的是旧状态，而且内部状态还包含线上协议没有的 AwaitHello；显式传入目标线上状态可以避免时序错误，也能避免依赖内部枚举值与协议状态码偶然相同。

### 164. 为什么单连接会话状态更适合定义在 `run()` 的当前客户端作用域，而不是 `TcpServer` 的公开静态成员？

**参考答案：**

会话状态属于一条具体 TCP 连接，应在接受客户端后初始化，并在连接结束时随作用域销毁。公开静态成员会被所有 TcpServer 实例和未来的多个连接共享，还可能在再次调用 run() 时保留旧状态，既破坏连接隔离，也给并发扩展留下数据竞争风险；局部状态通过引用传给帧处理函数更符合所有权边界。

### 165. 如果 ACK 已发送成功但紧随其后的 STATUS 发送失败，为什么服务端不能继续使用当前连接？

**参考答案：**

客户端已经看到命令成功 ACK，却没有收到对应的新状态，双方对命令是否完整完成的认识可能不一致。继续处理后续命令会放大这种状态歧义，因此应把发送失败视为致命连接错误并关闭连接；内部状态也只在 ACK 和 STATUS 都成功后提交，避免服务端在失败路径上继续携带一个对端未知的新状态。

### 166. 为什么模拟器内部的 `SessionState` 不应放在共享协议层的 `frame.h` 中？

**参考答案：**

`frame.h` 描述线上可传输的数据模型，而 `AwaitHello` 等状态属于服务端对单条连接的业务控制过程，并不是协议帧字段。把内部状态放进共享协议层会扩大依赖并诱导调用方把枚举底层值直接当作 STATUS 码；将其留在模拟器实现文件中可以保持协议层纯净，并明确内部状态与线上状态码需要显式映射。

### 167. 重复 HELLO 返回 `ERROR(BAD_STATE)` 后，为什么应保持连接和原会话状态，而不是主动断开或重新进入 READY？

**参考答案：**

协议错误表规定 BAD_STATE 不关闭连接，所以客户端仍可根据错误修正后续操作。重复 HELLO 没有成功执行，不能重置正在采集或空闲的会话；只返回错误并保持原状态，既符合“错误请求不改变状态”的规则，也避免一次多余握手意外中断正常控制流程。

### 168. 为什么 `git status` 干净且状态机修正已经提交，仍不能把 START/STOP 标记为“已验证通过”？

**参考答案：**

Git 只能证明当前文件与提交记录一致，不能证明源码能被目标编译器接受，也不能证明运行时行为符合协议。START/STOP 仍需在默认 MSVC 2022 + RelWithDebInfo 环境实际构建、运行协议回归，并通过真实 TCP 字节联调后，才能从“已实现但未验证”转为“已验证”。

**参考答案：**

多配置生成器在同一个构建树中同时维护 Debug、Release、MinSizeRel 和 RelWithDebInfo，目录名本身不能决定本次使用哪一套产物。构建时使用 `--config RelWithDebInfo`、CTest 时使用 `-C RelWithDebInfo`，才能确保编译、链接和测试发现都指向本项目冻结的默认验收配置，避免误用旧的 Debug 或其他配置结果。

**参考答案：**

当前 Catch2 主要覆盖协议编解码与 StreamParser，并不通过真实 Socket 驱动 `TcpServer` 的会话状态机。NetAssist 联调可直接检查 ACK、STATUS、ERROR 的线上字节、发送顺序、状态转换以及错误后连接是否保持，因此它补充的是协议单测尚未覆盖的端到端证据。

**参考答案：**

状态机验收不仅要求单条响应正确，还要求状态在同一连接内按指定顺序连续转换。当前成功 HELLO 的时间戳晚于 START、STOP 和再次 START，可能来自另一次连接或服务端重启；缺少对应连接的连续时序，就不能排除各分支分别正确但连接级状态衔接仍有问题。

### 174. 连续两次重复 HELLO 都收到 `ERROR(BAD_STATE)`，可以同时证明哪两个行为？

**参考答案：**

第一次 BAD_STATE 证明服务端在已经完成 HELLO 后拒绝重复握手且没有重新进入 READY；随后同一客户端还能发送第二次 HELLO 并收到完整 ERROR，证明第一次非致命错误没有关闭连接。两次响应相同还表明错误请求没有改变原会话状态。

### 175. 在 Running 状态发送重复 START 得到 `ERROR(BAD_STATE)` 后，为什么紧接着发送合法 STOP 是重要的验证步骤？

**参考答案：**

单独收到 BAD_STATE 只能证明错误码正确；随后合法 STOP 能返回 ACK(STOP)+STATUS(IDLE)，才同时证明服务端没有因非致命错误关闭连接，并且错误请求没有把 Running 状态错误地改变掉。这样把“错误响应、连接保持、状态保持”三个行为串成一条可观察证据链。

### 176. 在 Idle 状态发送采样率为 0 的 START 后，再发送合法 START，可以验证哪些边界？

**参考答案：**

非法 START 应只返回 BAD_PARAM，不发送 ACK，也不改变 Idle 状态或关闭连接；紧随其后的合法 START 若能返回 ACK(START)+STATUS(RUNNING)，就证明参数错误分支既保持了连接，也保持了允许重新启动的原状态。

### 177. 为什么本次日志中“错误请求之后的合法命令成功”比单独核对 ERROR 字节更能证明状态机正确？

**参考答案：**

ERROR 字节正确只能证明服务端选择了预期错误码；后续合法命令成功还证明该错误没有关闭连接、没有错误提交状态，也没有破坏解析器或会话。比如重复 START 后合法 STOP 成功，说明会话仍保持 Running；非法 START 后合法 START 成功，说明会话仍保持 Idle。

### 178. HELLO/START/STOP 手工联调全部通过后，哪些网络可靠性问题仍不能据此宣告已验证？

**参考答案：**

人工正常收发没有强制触发 `send()` 部分发送、Winsock API 失败、客户端复位、长期半包超时或多客户端连续接入；当前服务端也仍是单次 `accept()`。这些属于后续故障注入、自动化端到端测试或可靠性阶段的范围，不能由本次成功日志外推为已经通过。

## Winsock 指南｜select 与常用函数

### 179. 为什么每轮调用 select() 前都应从主集合复制一份新的 fd_set，而不能直接重复使用上次返回的集合？

**参考答案：**

readfds、writefds 和 exceptfds 都是输入/输出参数；select() 返回时会把集合改写为本轮真正就绪的子集。若下一轮直接复用这个结果，上轮未就绪的 Socket 已经从集合中消失，之后即使有事件也不会再被监视。应长期维护主集合，每轮复制一份临时集合交给 select() 修改。

### 180. 监听 Socket 和已连接客户端 Socket 同时出现在 select() 的 readfds 中时，“可读”分别表示什么？

**参考答案：**

监听 Socket 可读通常表示连接等待队列中已有客户端，此时可以调用 accept()；已连接 Socket 可读可能表示有数据、对端有序关闭，或连接发生复位/终止。因此客户端就绪后仍必须调用 recv()，并分别处理正字节数、0 和 SOCKET_ERROR，不能只凭 FD_ISSET() 推断具体结果。

### 181. 为什么不能把所有客户端永久放进 select() 的 writefds？

**参考答案：**

TCP Socket 在大多数时间都可写，永久监视会使 select() 经常立即返回，事件循环可能在没有待发送数据时高速空转并占用 CPU。只有连接存在尚未发送完的应用层缓冲时才应加入 writefds；缓冲清空后立即移除，而且就绪后的 send() 仍可能只完成部分发送。

### 182. 为什么把 Socket 放入 `select()` 的 `readfds`，仍不能防止当前 `send_all()` 阻塞整个多客户端事件循环？

**参考答案：**

`readfds` 只保证调用 `recv()` 前该 Socket 当前可读，并不约束后续 `send()`。当前客户端 Socket 仍是阻塞模式，`process_frame()` 会同步进入 `send_all()`；若某个客户端长期不读取、发送缓冲区耗尽，`send()` 就可能阻塞，事件循环无法再处理监听 Socket 或其他客户端。要实现可扩展的单线程多连接模型，需要非阻塞 Socket、仅在有待发送数据时监视 `writefds`，并保留部分发送进度。

### 183. 在多客户端服务器中，为什么某个连接返回 `CloseConnection` 时不能直接从 `TcpServer::run()` 返回？

**参考答案：**

`CloseConnection` 描述的是当前协议会话需要关闭，例如版本不匹配，并不表示监听服务或其他客户端都应结束。直接从 `run()` 返回会析构监听 Socket 和整个客户端容器，误伤所有其他连接；多客户端模型应只标记并移除当前 `ClientSession`，然后继续事件循环。

### 184. 为什么 `select()` 的 timeout 传 `nullptr` 无法承担 DATA 周期推流的节拍器职责？

**参考答案：**

空 timeout 会让 `select()` 一直阻塞，直到监听 Socket 或客户端 Socket 出现网络事件；当连接处于 Running 且客户端暂时不发送控制命令时，事件循环不会按采样截止时间醒来，因此无法周期生成 DATA。应根据最近的 DATA 截止时间计算有界 timeout，并在 `select()` 返回 0 时处理到期批次。

### 185. 为什么事件循环要比较 `state_before` 与处理后的 `session_state`，而不能只要看到 Running 就重置 DATA 截止时间？

**参考答案：**

只有成功 START 造成的“非 Running → Running”转换才代表新的采集会话开始。若每处理一帧后只检查当前状态为 Running，重复 HELLO、非法 START 或其他不改变状态的命令也会不断把截止时间推迟，导致 DATA 节拍被无关控制帧干扰。比较转换前后状态可以只在真正进入 Running 时建立新节拍。

### 186. 为什么 STOP 成功后可以暂时保留旧的 `next_data_deadline`，而不会继续触发 DATA tick？

**参考答案：**

是否把截止时间交给 `select()` 由 `session_state == Running` 门控。STOP 成功后状态变为 Idle，事件循环会把 timeout 指针保持为空，旧时间点不再参与等待；下一次成功 START 又会覆盖它。只要所有 tick 入口都受状态门控，清空时间点不是正确性的必要条件。

### 187. DATA 的线上时间戳使用 UTC Epoch 时，为什么事件循环的截止时间仍应使用 `steady_clock`？

**参考答案：**

UTC Epoch 是跨进程可解释的样本时间，需要由系统时钟生成；发送间隔则必须抵抗系统校时、手工改时或时区变化。`steady_clock` 保证单调前进，适合计算下一批截止时间和超时；两种时钟职责不同，不能用 DATA 的绝对时间戳直接驱动周期等待。

### 188. 为什么模拟器构建成功和协议单元测试通过，仍不能代替本轮的真实 TCP 联调？

**参考答案：**

构建只证明源码能在目标工具链中编译链接，协议单元测试主要覆盖编解码与流式解析；它们不会实际建立 Socket，也没有让 `select()` 在 Running 状态交替经历超时和控制字节就绪。因此仍需真实连接验证 START 后事件循环持续存活，且 STOP 能被及时接收并正确响应。

### 189. 当前 START 后没有收到 DATA 帧，为什么不应判定为测试失败？

**参考答案：**

当前小步明确只实现 DATA tick 调度骨架：超时发生时仅推进下一截止点，尚未保存 START 参数、生成样本或编码发送 DATA。此轮联调的验收对象是控制状态机和 STOP 响应能力；把“收到 DATA”列为标准会把尚未实现的下一阶段功能误当成本轮缺陷。

### 190. 为什么构建日志中的实际 `CL.exe` 路径和编译参数，比仅根据 `build` 目录名判断环境更可靠？

**参考答案：**

目录名只是人为命名，无法保证内部缓存、生成器或工具链没有被重新配置。实际构建日志会显示调用的 Visual Studio、MSVC 工具集路径、目标平台、配置和 `/std:c++17` 等参数，能直接证明本次参与编译的环境；同时仍应先检查 `CMakeCache.txt` 确认生成器与配置集合。

### 191. START 与 STOP 相隔约 15 秒仍能立即得到正确响应，主要验证了 DATA tick 骨架的什么性质？

**参考答案：**

这说明 Running 状态下事件循环可以反复因 20ms 截止时间醒来并推进下一截止点，同时仍持续把客户端 Socket 放入 `readfds`；STOP 到达后能够转入 `recv()` 和状态机处理，而没有被永久等待或空 tick 循环饿死。它验证的是当前无 DATA 发送条件下的控制通路可响应性，不代表未来大帧发送时的背压问题已解决。

### 192. NetAssist 的 STOP 发送与响应显示在同一毫秒，为什么仍不应宣称服务器延迟精确等于 0ms？

**参考答案：**

日志时间戳受工具的计时分辨率、线程调度、缓冲刷新和记录位置影响；同一毫秒只能说明没有观察到超过该显示粒度的延迟，不能证明真实耗时为零。若要给出精确延迟，应使用明确起止点的高分辨率计时并重复统计。

### 193. 规划文档与协议文档对 DATA `ts` 的定义冲突时，为什么线上字段使用 UTC Epoch，而调度仍使用 `steady_clock`？

**参考答案：**

仓库约定明确规定协议实现以 `Doc/协议文档.md` 为准，因此线上 `ts` 必须是可跨进程解释的 UTC Unix Epoch 微秒。发送节拍属于本机持续时间计算，需要抵抗系统校时和回拨，仍应使用单调的 `steady_clock`；两种时钟承担不同职责。

### 194. START 的 payload 长度已经验证为 5 时，为什么在成功响应后读取 `payload.at(6)`～`payload.at(9)` 会造成比普通参数错误更严重的后果？

**参考答案：**

长度为 5 的 vector 只有索引 0～4，`at(6)` 会抛出 `std::out_of_range`。更严重的是代码已经先向客户端发送 ACK(START, OK) 和 STATUS(RUNNING)，随后才抛异常并退出进程，导致线上成功响应与服务端实际生命周期矛盾。采样配置应复用已验证的 0～4 字节解析结果，并与状态一起在成功响应后原子提交。

### 195. 为什么把 DATA 发送放在调用 `select()` 前的 `now >= next_data_deadline` 分支，不能覆盖正常的定时到期？

**参考答案：**

正常流程是在截止时间尚未来到时把剩余时间交给 `select()`；到期后 `select()` 返回 0，程序直接进入 `ready == 0` 分支。若该分支只推进截止时间而不发送，下一轮看到的截止时间又在未来，前置的逾期分支不会执行，因此每个正常到期批次都会被跳过。定时到期处理应集中到一个明确入口。

### 196. 协议要求 `seq` 按通道独立递增时，为什么一个全局 `seq_` 即使当前每轮都发送所有通道，也不是合格的状态模型？

**参考答案：**

所有通道暂时同步发送时，一个全局值可能碰巧产生相同的线上序号，但它无法表达某个通道独立跳过、失败或启停后的状态，也无法按协议分别处理回绕。每个 `chanId` 应拥有自己的 `uint32_t` 计数器，并在约定的采集会话边界独立初始化和递增。
