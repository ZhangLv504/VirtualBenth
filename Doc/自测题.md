## W1/S2｜协议边界与控制语义

### 1. 为什么线上帧包含 `payload_len`，内存中的 `Frame` 却不建议保存它？

**参考答案：**

线上字节流没有 C++ 容器的边界信息，接收端必须依靠 `payload_len` 判断需要读取多少字节。内存中的 `Frame` 已使用 `std::vector<std::uint8_t>` 保存 payload，其长度可以由 `payload.size()`唯一推导。若同时保存 `payload_len`，修改 payload 后可能忘记同步长度，形成两个互相矛盾的数据源。因此编码时由 `payload.size()`计算长度，解码时先校验线上长度，再构造 `Frame`。

### 2. 为什么 payload 上限为 4096B 时，DATA 的最大 `cnt` 是 1020，而不是 1024？

**参考答案：**

DATA payload 除样本外还有 15B 固定字段：`chanId` 1B、`seq` 4B、`ts` 8B、`cnt` 2B。每个 `float32` 样本占 4B，因此：

```text
15 + 4 × cnt ≤ 4096
cnt ≤ floor((4096 - 15) / 4) = 1020
```

`cnt=1020` 时 payload 为 4095B；`cnt=1021` 时为 4099B，已经超限。

### 3. ACK 和 STATUS 分别解决什么问题？

**参考答案：**

TCP 负责字节可靠传输，但不表示对端业务已经成功处理命令。ACK 表示对端应用层已经识别并成功处理指定控制命令；STATUS 表示设备当前状态，既可以跟在控制命令后发送，也可以因设备状态自行变化而主动发送。STATUS 不能替代 ACK。

**纠偏要点：** ACK 不只是证明“对端收到字节”，而是确认应用层命令处理成功。

### 4. 为什么“同一连接最多一个待确认控制命令”可以暂时不设计 `request_id`？

**参考答案：**

任一时刻只有一条 HELLO、START 或 STOP 等待结果，因此收到的匹配 ACK 或 ERROR 可以唯一归属于当前命令，不需要额外关联编号。如果允许多条命令并发在途，仅凭命令类型无法可靠匹配请求与响应，此时才需要 `request_id`。

### 5. 为什么读到 `payload_len=4097` 后不能继续等待 payload？

**参考答案：**

4097 虽然能由 `uint16` 表示，但违反协议规定的 4096B 上限，可能来自数据损坏、错误实现或恶意输入。继续等待会让攻击者利用伪造长度占用缓存并拖延解析，因此解析器应立即把当前候选帧判为非法，滑动一个字节后重新寻找 magic。

**纠偏要点：** 4097 不一定是“长度计算错误”，更准确地说是“违反协议边界”。

### 6. 非法长度或 CRC 错误后，为什么只滑动一个字节，而不是按声明长度丢弃整帧？

**参考答案：**

当前 magic 可能是假起点，声明长度也不可信；它后面的任意字节都可能是真正合法帧的 magic 开头。一次丢弃整段可能跳过后续合法帧。滑动一个字节再搜索能保留所有可能的同步起点。固定帧最小长度为 8B，不存在“整帧长度为 0”；只有 payload 长度可以为 0。

## W1/S2｜时间戳设计

### 7. 为什么后一帧的绝对时间戳变小，不能直接判定网络乱序？

**参考答案：**

UTC Unix Epoch 时间来自系统墙上时钟，可能因 NTP 校时、人工修改或虚拟机时钟调整而跳变或回拨。帧顺序和丢帧应以每通道递增的 `seq` 判断；`ts` 用于跨系统时间关联和历史查询。时间戳回拨应记录为时钟异常，而不是直接认定网络乱序。

### 8. 为什么时间戳单位是微秒，不等于设备具有微秒级时间精度？

**参考答案：**

微秒只是字段的表示分辨率。实际精度还受操作系统时钟源、调度延迟、采样时刻定义、NTP/PTP 同步质量及硬件能力影响。协议可以保存到 1μs，但不能据此宣称测量结果具备 1μs 准确度。

### 9. ACK 超时为什么应使用单调时钟，而不能使用 UTC Unix Epoch 时间？

**参考答案：**

超时测量关心经过了多长时间，需要时间只向前推进。UTC 系统时间可能跳变或回拨，可能导致超时提前、延后甚至长时间不触发。`std::chrono::steady_clock` 等单调时钟适合测量持续时间；UTC Unix Epoch 时间适合记录事件发生的绝对时间。

## W1/S3｜Frame 数据模型

### 10. 为什么 `Command::Invalid` 不能被编码发送？

**参考答案：**

`Invalid=0x00` 是内存中的安全默认状态，用来暴露“尚未选择命令”的对象。它不是协议命令表中的合法线上值。编码器遇到 `Invalid` 应返回错误，防止默认构造的半成品对象被误发给对端。

### 11. 为什么当前的 `Frame` 不需要 `.cpp` 文件？

**参考答案：**

当前 `Frame` 只有枚举、常量和数据成员，没有需要放到翻译单元中的非内联函数实现。声明全部放在头文件即可。保留并编译空的 `frame.cpp` 只会增加无意义的构建输入；以后若加入适合放在源文件中的实现，再创建对应 `.cpp`。

## W1/S3｜Catch2 基础测试

### 12. `TEST_CASE` 和 `REQUIRE` 分别做什么？

**参考答案：**

`TEST_CASE` 定义一个可以独立运行和报告结果的测试场景，名称应描述被验证的行为。`REQUIRE(expression)` 断言表达式必须为真；如果为假，当前测试立即失败，并报告失败位置和表达式。一个测试用例可以包含多个相关断言。

### 13. 为什么检查 `enum class Command` 的数值时需要 `static_cast<std::uint8_t>`？

**参考答案：**

`enum class` 是强类型枚举，不会隐式转换为整数。这能减少把不同枚举或整数意外混用的问题。测试线上协议值时，需要显式转换为其底层类型，再与 `0x01`、`0x06` 等字节值比较。

### 14. 为什么要测试命令枚举的具体数值，而不只测试枚举成员是否存在？

**参考答案：**

命令数值属于设备端和上位机共同遵守的线上协议。枚举成员即使能够编译，只要某个数值被误改，双端就可能把同一个字节理解为不同命令。测试具体数值可以锁定协议映射，在后续修改时及时发现破坏兼容性的变更。
