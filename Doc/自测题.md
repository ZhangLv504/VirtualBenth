## W1/S2｜协议边界与控制语义

### 1. 为什么线上帧包含 `payload_len`，内存中的 `Frame` 却不建议保存它？

**参考答案：**

线上字节流没有 C++ 容器的边界信息，接收端必须依靠 `payload_len` 判断需要读取多少字节。内存中的 `Frame` 已使用 `std::vector<std::uint8_t>` 保存 payload，其长度可以由 `payload.size()`唯一推导。若同时保存 `payload_len`，修改 payload 后可能忘记同步长度，形成两个互相矛盾的数据源。因此编码时由 `payload.size()`计算长度，解码时先校验线上长度，再构造 `Frame`。

### 2. 为什么 payload 上限为 4096B 时，DATA 的最大 `cnt` 是 1020，而不是 1024？

**参考答案：**

DATA payload 除样本外还有 15B 固定字段：`chanId` 1B、`seq` 4B、`ts` 8B、`cnt` 2B。每个 `float32` 样本占 4B，因此：

```text
15 + 4 × cnt ≤ 4096
cnt ≤ floor((4096 - 15) / 4) = 1020
```

`cnt=1020` 时 payload 为 4095B；`cnt=1021` 时为 4099B，已经超限。

### 3. ACK 和 STATUS 分别解决什么问题？

**参考答案：**

TCP 负责字节可靠传输，但不表示对端业务已经成功处理命令。ACK 表示对端应用层已经识别并成功处理指定控制命令；STATUS 表示设备当前状态，既可以跟在控制命令后发送，也可以因设备状态自行变化而主动发送。STATUS 不能替代 ACK。

**纠偏要点：** ACK 不只是证明“对端收到字节”，而是确认应用层命令处理成功。

### 4. 为什么“同一连接最多一个待确认控制命令”可以暂时不设计 `request_id`？

**参考答案：**

任一时刻只有一条 HELLO、START 或 STOP 等待结果，因此收到的匹配 ACK 或 ERROR 可以唯一归属于当前命令，不需要额外关联编号。如果允许多条命令并发在途，仅凭命令类型无法可靠匹配请求与响应，此时才需要 `request_id`。

### 5. 为什么读到 `payload_len=4097` 后不能继续等待 payload？

**参考答案：**

4097 虽然能由 `uint16` 表示，但违反协议规定的 4096B 上限，可能来自数据损坏、错误实现或恶意输入。继续等待会让攻击者利用伪造长度占用缓存并拖延解析，因此解析器应立即把当前候选帧判为非法，滑动一个字节后重新寻找 magic。

**纠偏要点：** 4097 不一定是“长度计算错误”，更准确地说是“违反协议边界”。

### 6. 非法长度或 CRC 错误后，为什么只滑动一个字节，而不是按声明长度丢弃整帧？

**参考答案：**

当前 magic 可能是假起点，声明长度也不可信；它后面的任意字节都可能是真正合法帧的 magic 开头。一次丢弃整段可能跳过后续合法帧。滑动一个字节再搜索能保留所有可能的同步起点。固定帧最小长度为 8B，不存在“整帧长度为 0”；只有 payload 长度可以为 0。

## W1/S2｜时间戳设计

### 7. 为什么后一帧的绝对时间戳变小，不能直接判定网络乱序？

**参考答案：**

UTC Unix Epoch 时间来自系统墙上时钟，可能因 NTP 校时、人工修改或虚拟机时钟调整而跳变或回拨。帧顺序和丢帧应以每通道递增的 `seq` 判断；`ts` 用于跨系统时间关联和历史查询。时间戳回拨应记录为时钟异常，而不是直接认定网络乱序。

### 8. 为什么时间戳单位是微秒，不等于设备具有微秒级时间精度？

**参考答案：**

微秒只是字段的表示分辨率。实际精度还受操作系统时钟源、调度延迟、采样时刻定义、NTP/PTP 同步质量及硬件能力影响。协议可以保存到 1μs，但不能据此宣称测量结果具备 1μs 准确度。

### 9. ACK 超时为什么应使用单调时钟，而不能使用 UTC Unix Epoch 时间？

**参考答案：**

超时测量关心经过了多长时间，需要时间只向前推进。UTC 系统时间可能跳变或回拨，可能导致超时提前、延后甚至长时间不触发。`std::chrono::steady_clock` 等单调时钟适合测量持续时间；UTC Unix Epoch 时间适合记录事件发生的绝对时间。

## W1/S3｜Frame 数据模型

### 10. 为什么 `Command::Invalid` 不能被编码发送？

**参考答案：**

`Invalid=0x00` 是内存中的安全默认状态，用来暴露“尚未选择命令”的对象。它不是协议命令表中的合法线上值。编码器遇到 `Invalid` 应返回错误，防止默认构造的半成品对象被误发给对端。

### 11. 为什么当前的 `Frame` 不需要 `.cpp` 文件？

**参考答案：**

当前 `Frame` 只有枚举、常量和数据成员，没有需要放到翻译单元中的非内联函数实现。声明全部放在头文件即可。保留并编译空的 `frame.cpp` 只会增加无意义的构建输入；以后若加入适合放在源文件中的实现，再创建对应 `.cpp`。

## W1/S3｜Catch2 基础测试

### 12. `TEST_CASE` 和 `REQUIRE` 分别做什么？

**参考答案：**

`TEST_CASE` 定义一个可以独立运行和报告结果的测试场景，名称应描述被验证的行为。`REQUIRE(expression)` 断言表达式必须为真；如果为假，当前测试立即失败，并报告失败位置和表达式。一个测试用例可以包含多个相关断言。

### 13. 为什么检查 `enum class Command` 的数值时需要 `static_cast<std::uint8_t>`？

**参考答案：**

`enum class` 是强类型枚举，不会隐式转换为整数。这能减少把不同枚举或整数意外混用的问题。测试线上协议值时，需要显式转换为其底层类型，再与 `0x01`、`0x06` 等字节值比较。

### 14. 为什么要测试命令枚举的具体数值，而不只测试枚举成员是否存在？

**参考答案：**

命令数值属于设备端和上位机共同遵守的线上协议。枚举成员即使能够编译，只要某个数值被误改，双端就可能把同一个字节理解为不同命令。测试具体数值可以锁定协议映射，在后续修改时及时发现破坏兼容性的变更。

### 15. 为什么 CTest 显示 1 个测试，而 Catch2 报告 5 个测试用例？

**参考答案：**

CMake 的 `add_test` 把整个 `protocol_tests` 可执行程序注册为一个 CTest 测试，所以 CTest 显示 `1/1`。这个可执行程序内部包含多个 Catch2 `TEST_CASE`，由 Catch2 继续发现、执行并统计，因此本次报告为 5 个测试用例、21 个断言。两者统计的是不同层级。

### 16. 为什么验收时要确认构建日志中确实重新编译了 `test_frame.cpp`？

**参考答案：**

增量构建可能直接运行之前生成的旧测试程序。如果只看到测试通过，却没有确认新测试源文件已参与编译和链接，就可能把旧二进制的结果误认为当前代码的结果。本次构建日志明确出现 `test_frame.cpp` 并重新生成 `protocol_tests.exe`，因此后续测试结果可以证明当前 Frame 测试已实际执行。

## W1/S4｜ProtocolCodec 编码

### 17. 为什么编码 `payload_len` 和 CRC 时不能直接复制本机整数的内存？

**参考答案：**

本机整数的内存字节序取决于 CPU 平台，直接复制还可能受到类型大小、对齐和对象表示的影响；协议要求线上格式始终为显式小端。编码时应通过移位和掩码分别写入低字节、高字节，使结果与运行平台无关，也避免把 C++ 对象内存布局当成网络协议布局。

### 18. 为什么 CRC 从 `version` 开始计算，而不覆盖 magic 和帧尾 CRC？

**参考答案：**

这是冻结协议明确规定的覆盖范围：`version + command + payload_len + payload`。magic 用于在字节流中寻找同步起点；若 magic 损坏，解析器会把它当作噪声并继续寻找下一处 magic。帧尾 CRC 是待比较的校验结果，不能把自身加入计算，否则编码端和接收端无法按同一规则验证。

### 19. 为什么 `ProtocolCodec::encode()` 只校验帧级约束，而不在这一层检查 START 采样率或 DATA 的 `cnt`？

**参考答案：**

`ProtocolCodec` 的职责是把通用 Frame 安全地转换为线上字节，包括版本、合法命令、最大 payload、大小端和 CRC。START 参数、DATA 样本结构等属于具体命令的业务语义，应由构造命令 payload 的业务层或专门的 payload 编解码函数校验。分层可以避免通用帧编解码器不断膨胀，也让帧级测试与业务级测试彼此独立。

### 20. 把 payload 复制到输出缓冲区后，为什么必须同步推进写入位置 `pos`？

**参考答案：**

`pos` 表示下一个待写字节的位置。复制 payload 后如果不执行 `pos += payload_len`，后续 CRC 会从 payload 起始位置写入，覆盖 payload 的前两个字节；空 payload 因长度为 0 可能碰巧通过，从而掩盖这个错误。START 等非空 payload 的精确字节测试能够暴露该问题。

### 21. 调用 CRC 函数时，起始指针和长度应该如何确定？

**参考答案：**

协议规定 CRC 覆盖 `version + command + payload_len + payload`。完整缓冲区中 version 位于偏移 2，因此起始指针应指向 `bytes.data() + 2`，长度为 `4 + payload_len`。不能从 `bytes.data()`开始，也不能把 magic 或尚未写入的帧尾 CRC 空间纳入计算。

### 22. 为什么在 C++17 中不能直接写 `ProtocolCodec::encode(frame) == EncodeResult{}`？

**参考答案：**

自定义结构体不会在 C++17 中自动生成 `operator==`，而 `EncodeResult` 也没有手写比较运算符，因此该表达式无法编译。测试应分别检查语义，例如先保存结果，再使用 `REQUIRE(result.ok())` 和 `REQUIRE(result.bytes == expected)`。即使定义结构体整体相等，拿成功结果与默认的空结果比较也不能验证正确编码出的帧内容。

## 项目协作｜新会话交接

### 23. 为什么要把 `AGENTS.md` 与 `PROJECT_PROGRESS.md` 分开？

**参考答案：**

`AGENTS.md` 保存长期稳定、需要每次会话遵守的规则，例如导学方式、测试授权和文档优先级；`PROJECT_PROGRESS.md` 保存会频繁变化的当前阶段、验证证据、已知问题和下一步。分开后，稳定规则不会被进度细节淹没，也能避免旧阶段状态长期留在自动加载的指令中。

### 24. 为什么新会话读取 `PROJECT_PROGRESS.md` 后，仍然必须检查 Git 和实际文件？

**参考答案：**

进度文档只是某个时间点的人工摘要，可能尚未记录用户刚完成的编辑、暂存区变化或最新测试结果。Git 状态、diff、实际文件和真实测试输出才是当前事实。新会话先读摘要用于快速定位，再用这些证据核对，可以避免重复工作、覆盖未提交修改，或把“已经写入”误报为“已经验证”。

## W1/S4｜ProtocolCodec 编码审查

### 25. 为什么 payload 为空、复制长度为 0 时，仍不应无条件调用 `std::memcpy`？

**参考答案：**

空 `std::vector` 的 `data()` 允许返回空指针，而 `std::memcpy` 要求传入有效指针；不能把“复制 0 字节”当成空指针一定合法。HELLO 和 STOP 都有合法空 payload，因此编码器应仅在 `payload_len > 0` 时调用 `std::memcpy`，随后再统一推进写入位置。

### 26. 为什么 UnsupportedVersion 测试还应把 command 设置为一个合法命令？

**参考答案：**

一个测试最好只引入一个导致失败的条件。若版本非法且 command 仍为默认 `Invalid`，结果会依赖编码器先检查哪个字段；测试实际上锁定了错误检查顺序，而不是单独证明“不支持的版本会被拒绝”。把 command 设为 `Command::Hello` 后，失败原因才唯一来自 version。

### 27. 为什么只判断 `frame.command == Command::Invalid` 仍不能阻止未知命令被编码？

**参考答案：**

`enum class` 能防止普通整数被隐式赋值，但调用方仍可通过 `static_cast<Command>(0x55)` 构造一个枚举声明中不存在的值。只排除 `Invalid(0x00)` 会让该未知值被原样写入线上帧。编码器应明确接受当前协议定义的命令集合，其余未定义或预留值统一返回 `InvalidCommand`。

### 28. `std::vector<std::uint8_t>` 的 `operator==` 会比较什么？

**参考答案：**

它比较两个 vector 的元素数量以及每个对应位置的元素，只有长度相同且全部元素按顺序相等时结果才为真。因此 `result.bytes == expected` 可以验证完整帧的总长度、字节顺序和每个字节的值。

### 29. 在精确示例测试中，为什么 `result.bytes == expected` 后通常不必再单独断言长度？

**参考答案：**

vector 相等本身已经要求长度相同。如果实际结果多一个或少一个字节，相等比较就会失败。单独检查长度只有在希望把“长度错误”和“内容错误”分别报告，或者测试本身只关心长度边界时才有额外价值。

### 30. 为什么 `payload_len` 可以使用 `std::uint16_t`，而 `total_len` 和 `pos` 更适合使用 `std::size_t`？

**参考答案：**

`payload_len` 对应协议中固定的 2 字节无符号字段，使用 `std::uint16_t` 能表达其线上宽度。`total_len` 和 `pos` 用于表示 C++ 容器的大小与下标，应与 `vector::size()` 的类型一致，使用 `std::size_t` 可以避免有符号/无符号混用和不必要的窄化转换。

### 31. 为什么错误路径除了检查错误码，还应检查 `result.bytes.empty()`？

**参考答案：**

错误码证明编码器识别了非法输入，而空输出证明它没有同时泄漏一段不完整或不可发送的帧。两项一起断言，才能锁定“失败时不产生线上数据”的接口契约。

### 32. 为什么 4096B 边界测试还要检查编码后的长度字段和 payload 首尾字节？

**参考答案：**

只检查输出总长 4104B，无法证明 `payload_len` 被正确写成小端 `00 10`，也无法证明整个 payload 被放在正确位置。增加长度字段及 payload 首尾检查，可以更有针对性地发现端序错误、偏移错误或边界处漏写数据。

### 33. 为什么本次既要确认构建成功，又要确认测试成功？

**参考答案：**

构建成功只证明当前源码能够完成编译和链接，例如标准库头、类型名称和函数声明没有阻止生成程序；测试成功才进一步证明程序在已覆盖场景中的行为符合预期。测试程序无法生成时谈不上执行，能生成也不代表编码逻辑一定正确，因此两种证据缺一不可。

### 34. 为什么构建日志中重新出现 `protocol_codec.cpp` 和 `test_protocol_codec.cpp` 很重要？

**参考答案：**

这证明刚修改的实现和测试实际参与了本次编译，运行的不是修改前遗留的旧测试程序。只有重新编译、重新链接后得到的可执行程序，其测试结果才能作为当前工作区的验证证据。

### 35. 12 个测试用例、43 个断言全部通过，为什么还不能说明 `decode()` 已经完成？

**参考答案：**

测试结论只覆盖本次实际编译和执行到的功能。当前新增用例验证的是 encode，已有用例验证 Frame 和 CRC；`decode()` 尚未实现，也没有对应测试。通过数量不能替代覆盖范围分析，因此只能宣布 encode 里程碑通过，不能把后续功能一并视为完成。

### 36. 为什么 VS2022 Debug 测试通过，仍不能替代项目默认的 VS2019 RelWithDebInfo 验收？

**参考答案：**

不同编译器版本和构建配置可能暴露不同的问题，例如标准库实现差异、警告与优化行为、宏定义以及只在优化后出现的未定义行为。VS2022 Debug 通过是有价值的补充证据，但项目声明的默认交付环境是 VS2019 RelWithDebInfo，因此最终阶段结论必须包含默认环境的实际构建和测试结果。

### 37. 为什么项目可以同时使用“VS2019 工具链”和“Ninja 生成器”？

**参考答案：**

编译器工具链负责把 C++ 源码编译、链接成程序，本项目当前使用 VS2019 提供的 `cl.exe`；CMake 生成器负责生成并驱动构建规则，当前使用 Ninja。Ninja 可以调用 VS2019 的编译器，因此两者描述的是构建链的不同层次，并不冲突。

### 38. 新会话能够读取根目录 `AGENTS.md`，为什么仍建议发送新会话启动指令？

**参考答案：**

`AGENTS.md` 适合保存长期稳定的仓库规则；启动指令会明确要求新会话读取动态的 `PROJECT_PROGRESS.md`、核对 Git 和实际工具链，并指出当前唯一任务。两者配合既避免把易过期的进度塞进长期规则，也能让新会话快速恢复到正确阶段。

## 项目协作｜默认环境复验前核对

### 39. 为什么不能仅凭目录名 `cmake-build-relwithdebinfo` 判断默认构建环境？

**参考答案：**

目录名只是人为约定，可以被误命名、复制或保留旧配置；真正决定构建行为的是目录内的 CMake 缓存和编译器识别结果。运行前应核对 `CMAKE_BUILD_TYPE`、`CMAKE_GENERATOR`、`CMAKE_CXX_COMPILER` 以及编译器 ID/版本，才能确认当前目录实际使用的是 RelWithDebInfo、Ninja 和预期的 MSVC 工具链。

### 40. `git status` 中新文件显示 `AM` 时，为什么必须同时查看 `git diff` 和 `git diff --cached`？

**参考答案：**

`AM` 表示该新文件已经有一个版本进入暂存区，同时工作区又在暂存版本之上继续修改。`git diff --cached` 显示暂存区相对 HEAD 的内容，`git diff` 显示工作区相对暂存区的内容；只看其中一个会漏掉另一层变化，可能误判实际实现或在后续操作中覆盖用户工作。

### 41. CMake 缓存确认了 VS2019、Ninja 和 RelWithDebInfo，为什么仍不能说当前 encode 已在默认环境通过？

**参考答案：**

CMake 缓存只能证明该构建目录配置为这些工具和构建类型，不能证明最新源码已经被重新编译，更不能证明测试已经执行成功。只有在当前工作区上实际构建目标，并运行 CTest 与测试可执行程序、记录真实输出后，才能把 encode 标记为已在默认环境验证。
